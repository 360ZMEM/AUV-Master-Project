## 2. 当前源码关键发现

### 2.1 `Remote_Assignment()` 会重建主推和舵面输出

文件：

- `csd_vx6.8_lastest/DataProcess.c`

关键路径：

```c
void Remote_Assignment(_To_MCUFD *temp)
{
    ...
    if(UI_Channel_Selection_Down == 0x01)
    {
        (*temp).McuFD_Motor1_Set_Speed = UI_LORA_Instruction.FromUI12_Motor_Speed1;
    }
    if(UI_Channel_Selection_Down == 0x02)
    {
        (*temp).McuFD_Motor1_Set_Speed = UI_WIFI_Instruction.FromUI12_Motor_Speed1;
    }
    ...
    if(UI_Channel_Selection_Down == 0x02)
    {
        (*temp).McuFD_LH_Set_Rud_Location =
            (u16)(LH_Ref_Location - (UI_WIFI_Instruction.FromUI12_RCD_LH_Set_Rud_Angle) * 4096/360);
    }
    ...
    sprintf(ptr, "%05d", (*temp).McuFD_Motor1_Set_Speed);
    ...
    strncpy((char *)to_MCU_buf, ptr, strlen(ptr));
}
```

含义：

- `Remote_Assignment(&Instruction_To_FMCU)` 不是“只把现有 `Instruction_To_FMCU` 打包发送”。
- 它会重新读取 `UI_WIFI_Instruction` 或 `UI_LORA_Instruction` 的 shadow 字段，并覆盖 `Instruction_To_FMCU` 内的主推、侧推和舵面字段。
- 因此，在调用 `Remote_Assignment()` 之前直接写：

```c
Instruction_To_FMCU.McuFD_Motor1_Set_Speed = 300;
```

如果没有同步写入对应 shadow 字段，随后会被 `UI_WIFI_Instruction.FromUI12_Motor_Speed1` 或 LORA 字段覆盖。

这与实物 Telnet 现象一致：

- 舵面能进入 `Instruction_To_FMCU`。
- `motor1` 最终仍为 0。

### 2.2 `Seafloor_Grounding_Arbitration()` 的 BUG-5/BUG-6 自救主推存在覆盖风险

文件：

- `csd_vx6.8_lastest/SecurityEmergencyManage.c`

关键路径：

```c
Instruction_To_FMCU.McuFD_Motor1_Set_Speed = 300;
Remote_Assignment(&Instruction_To_FMCU);
```

以及：

```c
Instruction_To_FMCU.McuFD_Motor1_Set_Speed = 350;
Remote_Assignment(&Instruction_To_FMCU);
```

源码含义：

- DVL 丢底自救和硬阈值拉起逻辑先写 `Instruction_To_FMCU.McuFD_Motor1_Set_Speed`。
- 随后调用 `Remote_Assignment()`。
- 但 `Remote_Assignment()` 会重新用 UI shadow motor 字段覆盖主推。

当前判断：

- BUG-5/BUG-6 的根因高度集中在“自救输出没有以 `Remote_Assignment()` 可保留的方式进入最终 `$MCUFD` 打包路径”。
- 需要选择修复策略：
  1. 调用 `Remote_Assignment()` 之前同步写入 UI/LORA shadow motor 字段。
  2. 新增一个不会覆盖应急主推的 emergency 打包函数。
  3. 修改 `Remote_Assignment()`，增加 emergency override 标志或保护分支。

### 2.3 BUG-4 深度保护路径源码中已有 shadow 写入痕迹，但运行期仍未闭合

文件：

- `csd_vx6.8_lastest/SecurityEmergencyManage.c`

关键路径：

```c
if(Depth_Exceed_FromUI12_Depth_Para1 >= 10)
{
    Sys_Abnorm_Inf_Judgement |= 0x00000200;
    Instruction_To_FMCU.McuFD_Motor1_Set_Speed = 300;
    Instruction_To_FMCU.McuFD_LH_Set_Rud_Location = ...;
    Instruction_To_FMCU.McuFD_RH_Set_Rud_Location = ...;

    UI_WIFI_Instruction.FromUI12_Motor_Speed1 = 300;
    UI_WIFI_Instruction.FromUI12_RCD_LH_Set_Rud_Angle = -20;
    UI_WIFI_Instruction.FromUI12_RCD_RH_Set_Rud_Angle = -20;
    UI_LORA_Instruction.FromUI12_Motor_Speed1 = 300;
    UI_LORA_Instruction.FromUI12_RCD_LH_Set_Rud_Angle = -20;
    UI_LORA_Instruction.FromUI12_RCD_RH_Set_Rud_Angle = -20;

    Remote_Assignment(&Instruction_To_FMCU);
}
```

含义：

- 当前源码已经尝试处理 `Remote_Assignment()` 覆盖问题，即在 BUG-4 路径中同步写入 shadow 字段。
- 根据现有实物记录，BUG-4 需要拆成两个子结论：
  - `应急上浮执行命令链`：已经看到 `Instruction_To_FMCU` 与最终 `$MCUFD` 带出 `motor1=300` 和舵面值，执行链已闭合。
  - `Bit9 告警位`：运行期仍未看到 `Sys_Abnorm_Inf_Judgement & 0x00000200` 稳定保持，这一子问题仍未闭合。
- 2026-07-15 再次实机复验中，`Depth_Exceed_FromUI12_Depth_Para1` 已累计到 `19`，且 `UI/Current work_cmd` 全程保持 `0x00`；因此 BUG-4 现已基本排除“未触发到阈值”和“`0x91` 直接清位”的主假设，收敛为 **Bit9 自身的设置/保持路径问题**。
- 但运行期 BUG-4 Bit9 设置/保持仍未闭合，说明问题可能不在“源码完全没有写 shadow”，而在：
  - 实机运行镜像不是当前源码版本。
  - `Depth_Exceed_FromUI12_Depth_Para1` 没有累计到阈值。
  - `Current_State.Current_Dep` 或 `UI_WIFI_Instruction.FromUI12_Depth_Para1` 被运行期覆盖。
  - `Work_Cmd_Execute(0x91)` 会清零 `Sys_Abnorm_Inf_Judgement` 和深度保护计数器；若运行期有重复 `0x91`，Bit9 可能刚置位又被清掉。
  - PySide6 当前实现里 `set_work_instruct()` 会把 `self.work_instruct` 保持为 `0x91/0x92`，发送循环会持续带该值出包，而不是一次性脉冲。
  - `Sys_Abnorm_Inf_Judgement` 后续被其他路径清位。
  - `Remote_Assignment()` 后又被 MainCtrlTask 的 Remote/Jetson 路径再次覆盖。

### 2.4 DVL 结构偏移不能继续依赖旧脚本硬编码

文件：

- `csd_vx6.8_lastest/DataProcess.h`

结构：

```c
typedef struct
{
    u8 head_buf[3];
    int BI_X;
    int BI_Y;
    int BI_Z;
    float BI_V;
    bool BI_Valid_Flag;
    float BD_Height;
    float BD_Time;
    float BD_Check;
    ...
}_From_DVL;
```

当前脚本曾按经验使用：

- `BD_Height = DVL_Prase_Data + 0x18`
- `BD_Check = DVL_Prase_Data + 0x20`

风险：

- `head_buf[3]` 后面存在 `int`、`float`、`bool`，VxWorks 编译器可能插入对齐 padding。
- `bool` 大小也可能影响后续 `float` 对齐。
- `AgreedTerms.h` 中 `int16`/`int32` 的 typedef 与常规直觉并不一致，不能直接把宿主机 `offsetof` 结果当成板端真值。
- 手算偏移不可靠。

- 脚本能完成 Telnet 连接、suspend、execute、resume、cleanup。
- 2026-07-15 live 复验中，`soft/hard/lost` 三组 case 里 `BD_Check/BD_Height` 仍读回 0。
- `Sys_Abnorm` 仍未直接置 Bit11/Bit12/Bit13。
- 但 `hard/lost` 已能观察到 `Instruction_To_FMCU` 的主推/舵面变化，说明仲裁分支存在部分运行期响应。

新的判断：

- DVL 自动化流程已基本稳定。
- 未闭合点主要是结构偏移/运行期覆盖/仲裁触发条件，而不是 Telnet execute 框架本身。
- DVL 问题需要拆成两层：
  - `DVL_Prase_Data` 真正偏移/对齐未闭合；
  - DVL 告警 Bit 未闭合，但控制输出链已有部分闭合迹象。

### 2.5 `EmergencyTask` 调度频率与触发阈值

文件：

- `csd_vx6.8_lastest/main.c`
- `csd_vx6.8_lastest/SecurityEmergencyManage.c`

关键路径：

```c
wdStart(wdTimer_InfoOutputCtrl, sysClkRateGet()*0.1, ...);
...
if(Emergency_Task_Interval_Num >= Emergency_Task_Period)
{
    semGive(semEmergencyTask);
    Emergency_Task_Interval_Num = 0;
}
```

`SecurityEmergencyManage.c` 注释写明 `EmergencyTask` 是 10Hz 安全仲裁。

含义：

- BUG-4 深度超限计数阈值 `>=10`，约对应 1 秒。
- BUG-5/BUG-6 DVL 丢底计数阈值 `>=20`，约对应 2 秒。
- Telnet 注入测试必须维持状态超过这些窗口，否则不能期望置位。

### 阶段 A：只读源码审计与已有证据固化

目标：不改源码，先把关键函数、真实数据路径、运行期现象解释串起来。

本阶段已完成的关键结论：

1. `BUG-4`：
   - 深度超限路径源码确实会置 `Bit9`，并同步写 shadow 主推/舵面。
   - live 复验已证明执行链闭合，未闭合点收缩为 `Bit9 为什么没有保持`。
2. `BUG-5/BUG-6`：
   - `Remote_Assignment()` 会用 UI/LORA shadow 重新覆盖主推和舵面。
   - DVL 自救路径先写 `Instruction_To_FMCU.McuFD_Motor1_Set_Speed`，随后调用 `Remote_Assignment()`，存在主推被覆盖的直接风险。
3. `DVL`：
   - `Seafloor_Grounding_Arbitration()` 直接读 `DVL_Prase_Data.BD_Check` / `BD_Height`。
   - `Unpack_Data_From_DVL_BD()` 是按 ASCII 帧解析并用 `atof()` 写字段，不是二进制协议拷贝。
4. `$AUV` 上行：
   - `Sys_Abnorm_Inf_Judgement -> Current_State.Current_Sys_Abnorm_Inf -> ToUI12_Sys_Abnorm_Inf` 链路已对齐，当前看不到 Bit 不是上行打包问题。

阶段 B 产出：

截至 2026-07-15 晚间，阶段 B 已新增的关键 live 证据：

1. `BUG-4 Bit9`
   - 使用增强版 `vxworks_bug4_runtime_probe.py --observe-each-cycle` 连续触发 `semEmergencyTask` 13 次。
   - 观测结果：
     - `Depth_Exceed_FromUI12_Depth_Para1` 从 `3 -> 52` 持续累积。
     - `UI/Current work_cmd` 全程保持 `0x00`。
     - `to_MCU_buf` 从第 3 个 cycle 起稳定出现 `motor1=00300`。
     - `Sys_Abnorm_Inf_Judgement` 在全部 cycle 中始终为 `0x00000000`。
   - 当前结论：
     - BUG-4 已不再是“执行链未触发”的问题。
     - 现阶段更接近 `Bit9` 在当前镜像/当前变量路径中“未真正置入可观测的 Sys_Abnorm_Inf_Judgement”，而不是简单的 `0x91` 清位问题。

2. `DVL 注入路径`
   - 原始 `vxworks_dvl_runtime_probe.py --execute --case all --suspend-runtime-tasks` 现象仍是：
     - `hard/lost` 可驱动 `Instruction_To_FMCU` 变化；
     - 但脚本读到的 `BD_Check/BD_Height` 仍显示 `0.000`。
   - 随后改用 Telnet 原始命令直接对 `DVL_Prase_Data + 0x18/+0x20` 写入：
     - 写入后立即读回可见 `PRE_H=0x3f99999a`、`PRE_C=0x40000000`。
     - 单次调用 `Seafloor_Grounding_Arbitration()` 后，字段仍保持不变，且 `POST_SYS=0x00000800`。
   - 当前结论：
     - `BD_Height/BD_Check` 本身不是“写入后被仲裁函数立即清零”的问题。
     - DVL 这条当前更偏向“原 probe 注入方法/观测方法有问题”，而不是 VxWorks 运行期覆盖。

3. `BUG-5/BUG-6 主推覆盖`
   - 使用 Telnet 原始命令构造：
     - `UI_Channel_Selection_Down = 0x02`
     - `UI_WIFI_Instruction.motor1 = 0`
     - `Instruction_To_FMCU.motor1 = 350`
   - 直接调用 `Remote_Assignment(Instruction_To_FMCU)` 后，`to_MCU_buf` 中最终帧出现：
     - `...,DZ,00000,00000,...`
   - 当前结论：
     - 已有 live 证据直接支持：`Remote_Assignment()` 会把应急/自救主推重新覆盖回 UI shadow 的 `motor1`，这是 BUG-5/BUG-6 的直接根因之一。

  2. BUG-5/BUG-6：已由源码审计 + live 调用共同支持 `Remote_Assignment()` 主推覆盖。
  3. DVL：已确认当前主要问题在 probe 注入/观测路径，不在仲裁后覆盖。
- 暂不建议现在转入 `GUI 调试`：
  - 因为 GUI 仍会把当前固件侧未收口问题包装成更复杂的并发现象，不利于先做最小侵入修复。

### 阶段 D：VxWorks 最小侵入修复设计

目标：基于阶段 A 证据，设计最小修改，不急于大改。

候选修复方向：

1. 新增 emergency-safe 打包函数。
   - 例如 `Emergency_Assignment(_To_MCUFD *temp)`。
   - 只更新时间戳、包头、包尾、`to_MCU_buf`。
   - 不从 `UI_WIFI_Instruction`/`UI_LORA_Instruction` 覆盖 motor/rudder。
   - 适合 BUG-4/5/6 的应急最终裁决输出。

2. 修改 `Remote_Assignment()`，增加 override 标志。
   - 例如全局 `Emergency_Output_Override_Flag`。
   - flag 为 true 时跳过 UI shadow 覆盖 motor/rudder。
   - 风险：影响面比新增函数更大。

3. 在所有应急路径调用 `Remote_Assignment()` 前同步写 shadow 字段。
   - BUG-4 已有类似做法。
   - BUG-5/BUG-6 可以补齐。
   - 风险：shadow 本身会被上位机新包覆盖，而且会污染 UI shadow 语义。

推荐优先级：

1. 优先考虑新增 emergency-safe 打包函数。
2. 如果工程风险不允许新增函数，再考虑应急路径同步写 shadow。
3. 不建议直接大改 `Remote_Assignment()` 作为第一步。

所有源码修改必须遵循：

- 修改前备份原文件，例如 `SecurityEmergencyManage_bak_20260711_bug56.c`。
- 源码文件保持 GB18030 编码。
- 修改块头部添加显眼 Doxygen 注释：

```c
/**
 * @brief BUG-5/BUG-6 应急输出保持修复
 * @date 2026-07-11
 * @author 清华 AUV 课题组
 * @note 避免 Remote_Assignment() 从 UI shadow 覆盖应急主推/舵面。
 */
```
