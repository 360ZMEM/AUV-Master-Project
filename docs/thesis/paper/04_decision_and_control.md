# 第 4 章：决策与控制系统

## 4.1 引言

第 2 章给出了系统硬件骨架，第 3 章解决了"AUV 在哪里、对自己有多大把握"的问题。本章接着回答下一个问题：在已有状态估计的基础上，如何把"去哪里巡检"和"怎样安全到达"两件事拆解成可工程化的决策与控制结构？回答这一问题之前，必须先澄清两个被工程实践反复证明的认识——第一，AUV 在水平方向是欠驱动的，这意味着控制器无法直接命令横向位移，只能通过航向调节间接实现；第二，水下巡检任务由"任务调度、轨迹生成、参考生成、低层执行、安全仲裁"五类截然不同的语义负载构成，把它们塞进同一个控制器既不现实也不安全。本节按这两个认识展开。

### 4.1.1 欠驱动 AUV 运动约束分析

AUV 通常采用 REMUS 100 型布局：尾部一个主推进器和两个十字形舵面（水平舵 + 垂直舵）。这种构型在水平面内可以通过舵角控制航向和前进速度，但在横移方向上没有直接执行器，属于典型的欠驱动系统。垂直面内通过水平舵控制俯仰角，间接改变深度。这种约束决定了：控制器不能期望在横移方向上产生直接力，而必须通过航向调节实现间接横向位移。换句话说，所有"沿电缆中心线保持横向偏移为零"的目标，最终都要被翻译成"调整航向使 AUV 朝中心线靠拢"——这个翻译过程正是 LOS 制导和 MPC guidance-level 参考生成存在的根本动机。

PVS 仿真中，AUV 接受 5 元控制命令 `[surge, sway, heave, yaw_rate, pitch_rate]`，映射为 `rudder_angle`（垂直舵）、`stern_angle`（水平舵）和 `rpm`（推进器转速）。执行器具有一阶惯性动态——舵角和推力的实际响应滞后于命令，时间常数在百毫秒量级。这种滞后看似细节，却直接决定了 MPC 的预测时域不能太短：如果时域只覆盖 0.5 s，模型还来不及"感受到"舵效就要给出最优解，预测意义就被掏空。本文据此把 MPC 预测时域设为 2 s（20 步 × 0.1 s），以充分覆盖一阶惯性的过渡过程。

控制对象的状态向量保留 6 个变量：`X = [x, y, z, ψ, u, w]^T`，其中 `x, y` 为 NED 平面位置（m），`z` 为 NED 深度（m，正向下），`ψ` 为航向角（rad），`u` 为前向速度 surge（m/s），`w` 为垂向速度 heave（m/s）。横向速度 `v`（sway）不被控制，而是通过 `ψ` 偏转间接影响 `(x, y)` 轨迹——这正是欠驱动约束在状态向量层面的直接体现。俯仰角 `θ` 在控制器中按目标深度误差近似生成，不作为独立状态量进入预测模型，这一选择牺牲了俯仰动力学的精确性，但显著降低了优化问题的维度，使 IPOPT 求解时间维持在控制周期可接受范围。

### 4.1.2 决策与控制系统的分层解耦逻辑

理解了欠驱动约束之后，下一个问题是：如何在系统层面组织决策与控制的不同职责？AUV 海缆巡检任务需要把"去哪里巡检"、"如何沿电缆走"、"感知不可靠时如何降级"和"出现安全风险时如何退出"放在同一个系统中处理——这四类问题的时间尺度、确定性程度和失败代价完全不同，把它们硬塞进一个控制器只会让代码不可维护、调试不可定位。本文据此采用分层解耦设计：

| 层级 | 职责 | 实现 |
|---|---|---|
| 任务调度层 | 决定当前应处于搜索/锁定/跟踪/上浮/返航/急停哪个阶段 | 行为树（Behavior Tree） |
| 轨迹生成层 | 根据任务阶段产生参考路径和参考速度 | 之字形扫描 + 电缆跟踪轨迹 |
| 参考生成层 | 把参考路径转化为航向/深度/速度指令 | LOS / MPC guidance-level |
| 低层控制层 | 把参考指令转化为舵角和推力 | PID/PVS depthHeadingAutopilot |
| 安全仲裁层 | 监控感知、通信和执行器状态，必要时限制或回退输出 | CommandGuard + failsafe 节点 |

这种分层在工程上有两个直接好处：一是允许各层独立验证（行为树可在不连接 MPC 的情况下用 mock action 验证调度逻辑，MPC 可在不连接行为树的情况下做控制 sweep）；二是允许各层独立替换（PID 替 MPC 不影响行为树，行为树替 FSM 不影响控制层）。整套系统的总体软件结构与节点拓扑参见架构图：

## 4.2 基于行为树的任务规划与调度

确定了分层架构之后，第一个需要具体实现的层就是任务调度层。在工程实践中，可选的实现方式主要有两类——传统的有限状态机（FSM）和现代的行为树（Behavior Tree, BT）。FSM 直接、易写、易理解，但对"应急优先级抢占"和"任务可组合"的支持极为薄弱：每加一种新故障类型，都要在所有相关状态之间画新的转移边，状态数膨胀很快变成 O(n²) 量级。行为树则把"组合"作为第一公民，应急行为可以以"高优先级 Selector 子树"的形式被插入到任意位置，而不破坏主任务的逻辑。本文据此选择行为树作为任务调度层的实现。

### 4.2.1 行为树节点设计

行为树由控制节点（Sequence、Selector、Parallel）、条件节点（Condition）和行动节点（Action）组成。条件节点检查系统状态并返回成功、失败或运行中；行动节点执行具体操作。控制节点负责按既定语义组合子节点，本文采用 Selector + Sequence 组合实现"应急优先 + 主线任务"的优先级抢占模型。具体而言，根节点为 Selector，第一子节点为应急 Sequence（电池/漏水/失联检查 + 紧急行动），第二子节点为主任务 Sequence（搜索 → 锁定 → 跟踪）。Selector 按从左到右的顺序检查子节点，只要应急 Sequence 中任一条件被触发，主任务就会立即被抢占——这种"优先级即顺序"的设计让代码层面不需要任何显式的"中断"或"信号"机制，所有抢占语义都通过节点排列直接表达。

| 节点类型 | 名称 | 职责 |
|---|---|---|
| Condition | `isBatteryOk` | 检查电池电压是否高于安全阈值 |
| Condition | `isCableDetected` | 检查声磁观测是否确认电缆存在 |
| Condition | `isCommunicationOk` | 检查与上位机/执行层的通信状态 |
| Condition | `isSafetyMarginViolated` | 检查离底高度是否低于安全阈值 |
| Action | `searchPattern` | 执行之字形扫描搜索 |
| Action | `cableTracking` | 沿电缆中心线跟踪 |
| Action | `emergencySurface` | 紧急上浮到安全深度 |
| Action | `returnToHome` | 返回起始位置 |

### 4.2.2 巡检任务逻辑流

上一节给出了行为树的节点设计，本节进一步回答：这些节点如何被组织成具体的巡检任务流程？为什么把巡检流程切成"搜索 → 锁定 → 跟踪 → 异常处理"这四阶段，而不是直接做"端到端跟踪"？答案来自对真实巡检场景的两点观察：第一，AUV 入水后的初始位置不一定恰好在电缆正上方——海图先验可能有数十米量级的偏差，必须先用扫描模式扩大可探测范围；第二，从"看见电缆信号"到"获得稳定的相对位置估计"之间存在一个必经的过渡过程——观测刚出现时往往噪声大、置信度低，直接进入跟踪会导致控制器频繁修正错误目标。这两点决定了"探测能力的逐步建立"必须被显式建模成不同阶段，而不能压缩成单一控制环。基于此，巡检任务被组织为四个互斥但可抢占的阶段：

1. **搜索阶段（Zig-zag）**：在未知区域执行之字形扫描，扩大探测范围，等待声磁观测确认电缆。该阶段的输入是初始位姿和先验路由区域，输出是连续多帧的稳定声磁检测结果，退出条件是"声磁两个通道在连续 N 帧内同时报告高置信度"。
2. **锁定阶段**:在声磁检测确认电缆存在后,把粗略的电缆位置估计逐步收敛到稳定的相对位置估计上,期间速度通常被压低到搜索阶段的一半左右,以让 EKF 在低动态条件下完成观测融合。退出条件是"相对位置估计的协方差降至跟踪阶段允许的阈值以下"。
3. **跟踪阶段**:沿电缆路由持续更新航向、速度和离底高度,同时监控感知质量和安全约束。该阶段是巡检任务的"主线工作模式",大部分有效观测和有效作业里程都在此阶段产生。退出条件包括"任务完成"、"感知质量退化触发降级"、"安全约束被违反触发应急"三类。
4. **异常处理**:当感知不可靠时降低速度或切换回搜索模式;当安全约束被违反时触发紧急上浮。该阶段不是独立的"工作模式",而是其他三阶段在异常条件下的临时退出路径——退出后可以根据恢复情况返回相应的正常阶段或进入应急 Sequence。

四阶段之间的转换由"关键观测信号"驱动,而非时间表驱动:从搜索切换到锁定依赖声磁检测的"高置信度持续帧数",从锁定切换到跟踪依赖 EKF 协方差的下降,从跟踪退出到异常处理依赖感知健康字段的变化。把转换条件设计成"观测驱动"而非"时间驱动"的好处是——任务流程对实际场景的快慢变化具有自适应能力,而不会因预设时间表与实际节奏不符而陷入僵硬执行。行为树相比 FSM 的核心优势在此进一步显现:四阶段之间的转换关系不需要画成"O(n²) 转移边",而只需要在 Sequence 节点的子节点之间按顺序排列条件检查,转换语义自动由节点返回值的成功/失败/运行中传播实现。

### 4.2.3 应急自救行为的优先级机制

正常任务流程之上，行为树还必须回答最后一个问题：当多种故障同时出现时，AUV 应该按什么顺序响应？这一问题的答案不能由编程偏好决定，而必须从"故障的不可逆性 + 响应的时间紧迫性"两个维度推出。Failsafe 节点对低电压、漏水、失联、传感器失效和控制器异常保持比所有正常任务更高的优先级，且五类故障内部也存在严格的优先级排序：漏水 > 失联 > 低电压 > 控制器异常 > 传感器失效。这一顺序的依据是——漏水一旦发生即对舱内电气和电池构成不可逆损坏威胁，必须立即上浮;失联意味着上位机失去对 AUV 的控制权,继续执行任何自主行为都可能造成物理后果不可控;低电压虽紧迫但仍允许"返航式"渐进退出;控制器异常可由 PID baseline 接管而不影响安全裕度;传感器失效中最常见的 DVL 短时丢包则只需降速等待恢复。换言之,优先级排序的本质是"哪类故障留给系统的反应时间最短",而不是"哪类故障最常见"。当任一安全条件被违反时,行为树中断当前任务,切换到相应的应急行为。

| 故障类型 | 触发条件 | 响应行为 |
|---|---|---|
| 低电压 | 电池电压低于阈值 | 上浮到安全深度 + 返航 |
| 漏水 | 漏水传感器触发 | 立即上浮 + 急停 |
| 失联 | 与 AMD/VxWorks 通信超时 1 s | 执行器停机（VxWorks 侧失联保护） |
| 传感器失效 | DVL/声呐/磁场连续异常 | 减速 + 切换到搜索模式 |
| 控制器异常 | MPC 求解超时或发散 | 回退到 PID baseline |

具体到检测机制：电池电压通过 AMD 上行 `$AUV` 帧中的电压字段定期采样,采用"连续 N 帧低于阈值"的滤波避免单帧噪声误触发;漏水信号由舱内多路漏水传感器经"任一通道触发即报警"的或运算输出,不做任何滤波——漏水检测宁可误报也不可漏报;通信失联由 Jetson 侧维护的"上次收到 `$AUV` 帧时间戳"在每个控制周期检查,1 s 阈值由"控制周期 100 ms × 10 倍冗余"反推;DVL/声呐/磁场异常由各自的健康字段累计计数,超过阈值后触发减速降级;MPC 求解器异常则由 IPOPT 的返回状态直接捕获。这五个检测路径在代码上彼此独立——任何一条出问题不会影响其他检测的工作,这是"安全检测路径冗余"在工程上的具体体现。

## 4.3 不确定的感知轨迹生成策略

任务调度层决定了"当前应该做什么"，下一个问题是"按什么样的几何路径去做"。在工程实践中，这一问题被进一步拆解为两个互补的子问题：第一，搜索阶段需要一条能够覆盖未知区域的扫描轨迹；第二，跟踪阶段在感知质量发生变化时，需要一种能够在"激进巡检"与"保守等待"之间动态切换的航速规划机制。前者关注空间几何，后者关注时间动态——两者共同决定了 AUV 在不同感知条件下走什么样的物理路径。

### 4.3.1 对齐行业标准的"之字形"空间扫描轨迹设计

之字形扫描是 AUV 海底巡检最常用的预扫描模式，但其参数选择并非随意——核心约束来自"探测覆盖率必须高于行业标准要求的下限"。本节按行业标准对探测覆盖率的要求，阐述扫描间距设计原则。扫描间距应根据声呐波束宽度和磁传感器有效探测距离确定，确保相邻扫描带之间有足够的重叠，避免漏检。

具体而言，扫描间距 `d` 的选择遵循一个简单原则：相邻两条扫描带的探测圆角覆盖区域必须有不小于 20% 的重叠，以容忍 AUV 实际航迹相对规划路径的横向偏差。给定声呐有效横向探测距离 `R_sonar` 和磁传感器有效探测距离 `R_mag`，本系统取 `d = 0.8 × min(2·R_sonar, 2·R_mag)`，其中"取最小值"是为了让两个传感器都满足覆盖率要求，"乘 0.8"则提供了 20% 的重叠裕度。这种取法看似保守——扫描间距越小、单位面积扫描时间越长——但工程上的代价远低于"漏检"带来的代价：一旦因间距过大而错过电缆，整个搜索阶段必须从头开始，反而比"稍微保守一些"花费更多时间。

> **表格占位符**：正式论文中需补充扫描间距计算公式、不同波束宽度下的扫描带宽度表和覆盖率统计表。

### 4.3.2 基于感知置信度的动态航速规划模型

空间扫描的几何决定后，下一个问题是时间维度的速度调节。在巡检阶段，AUV 不应当总是以恒定速度前进——感知置信度变化时，应当让"行驶节奏"也随之变化。一个简单的直觉是：当感知质量稳定时，AUV 可以以设计速度沿电缆巡检；当感知置信度降低时，控制器应降低航速，增加安全裕度。把这一直觉量化下来的核心，是把感知不确定性映射为速度上限的连续调节函数，而不是仅在"正常 / 异常"两种离散状态之间硬切换。

为什么不用硬切换而要用连续映射？原因有两点：第一，硬切换会在置信度阈值附近产生抖动——当置信度在阈值上下小幅波动时，速度上限会反复跳变，导致 AUV 不停地加减速；第二，连续映射允许"轻度退化时小幅减速、严重退化时大幅减速"，把可用感知信息按比例利用，而不是粗暴地把所有不可靠观测一律降级。本机制与 UA-MPC 的权重调整机制深度耦合。具体而言：

1. **感知置信度到速度上限的映射**：系统维护一个实时置信度值 `confidence ∈ [0, 1]`，由 ES-EKF 的协方差矩阵经 `cov_to_conf` 模块计算得到。当置信度低于 `confidence_threshold`（默认 0.6）时，参考速度 `target_speed_mps` 随置信度下降而降低，形成"感知越不可靠、行驶越保守"的行为。

2. **与 UA-MPC 权重联动的闭环**：置信度降低不仅导致速度上限下降，同时触发 UA-MPC 内部代价函数的动态调整——增大控制惩罚权重（使指令变化更平滑），放大跟踪权重（在已知参考附近保持保守跟随）。这种联动机制确保速度和参考生成两个通道都响应不确定性变化。换言之,速度通道决定"走多快",权重通道决定"走多稳",两者协同地把"感知不确定"翻译成 AUV 物理行为的双重保守。

3. **降级策略的层次化响应**：第一级为速度调节（confidence > 0.3），第二级为切换到搜索模式（confidence ∈ [0.1, 0.3]），第三级为紧急上浮（confidence < 0.1）。三级响应不是相互替代,而是在置信度持续恶化时按梯度逐级触发——"先减速等待,再退回搜索,最后上浮"——给系统提供从轻度退化到严重退化的连续应对手段。

完整链路为：ES-EKF 协方差 → `cov_to_conf` → `confidence` → UA-MPC 代价权重 + 参考速度。详见第 3 章。

## 4.4 不确定性感知模型预测控制设计

任务调度层和轨迹生成层都已就位之后，本章最关键的一层——也是本文最主要的算法贡献——是不确定性感知的模型预测控制（UA-MPC）。在进入具体公式之前需要先澄清一个工程上的定位问题：MPC 在本系统中并不是直接驱动舵机的低层控制器，而是 **guidance-level 参考生成器**。把它放在这一定位上的理由有两条——第一，PVS 内置的 `depthHeadingAutopilot` 已经是一个调优良好的 PID 内层，强行用 MPC 替代不会带来额外收益反而引入不必要的求解时间；第二，MPC 的真正优势（多变量耦合、约束处理、未来预瞄、不确定性权重）在 guidance level 上才能充分体现，而不是在单一深度闭环中。本节按"模型 → 代价 → UA 权重 → 参考 → 约束 → 求解器"六个层次依次展开。

### 4.4.1 离散化运动学预测模型

按上述路线，本节首先回答"模型层"应当采用什么样的状态空间表示。MPC 是一种"模型驱动"的控制方法——预测模型是它的全部物理依据，模型设计的合理性直接决定后续代价函数和约束讨论是否有意义。本节从两个问题入手：第一，状态向量应当取多少维？第二，离散化应当采用哪种数值方案？

先看状态向量的维度选择。Fossen 的 6-DOF 全自由度模型把刚体运动分为三个平动（surge、sway、heave）和三个转动（roll、pitch、yaw），状态向量共 12 维（6 自由度 × 位形和速度各一份）。但本系统的 MPC 不需要承担这一全套——理由有三：第一，REMUS 100 型欠驱动 AUV 在水平面没有横向执行器，sway 速度由 yaw 偏转间接产生，把 sway 作为独立状态量不会带来控制自由度，反而把求解维度推高一倍；第二，roll 在巡检任务中本就被 PVS 内层小角度近似抑制，把它纳入预测模型只会让动力学方程变得复杂；第三，pitch 由"目标深度 - 当前深度"的误差经 PID 限幅近似生成，作为派生量进入 heave 通道即可，并不需要独立状态。综合上述考虑，本系统把 MPC 状态向量精简为 6 维：

```
X = [x, y, z, ψ, u, w]^T
```

其中 `(x, y)` 为 NED 平面位置（m），`z` 为 NED 深度（m，正向下），`ψ` 为航向角（rad），`u` 为前向速度 surge（m/s），`w` 为垂向速度 heave（m/s）。这一选择在"够用即可"和"求解时间可控"之间取了一个工程平衡——既能描述路径预瞄和深度调节的核心动力学，又把 IPOPT 单步求解时间维持在控制周期可消化的范围。

控制量精简为 3 维：

```
U = [ψ_cmd, z_cmd, T_cmd]^T
```

这一选择再次呼应了"guidance-level reference generator"的定位：MPC 输出的不是舵角和转速本身，而是航向参考、深度参考和推力百分比，由 PVS/AMD 内层执行器在每个控制周期内消化为具体的舵面动作和转速。MPC 自身不直接产生舵角指令，而通过参考量的高频更新影响内层闭环行为——这种"上层只给目标、下层负责落实"的解耦使 PID 调优良好的内层得以保留，同时把多变量耦合和约束处理交给 MPC 优化器去做。

把上述状态向量与控制量代入连续时间动力学方程：

```
dx/dt  = u · cos(ψ)
dy/dt  = u · sin(ψ)
dz/dt  = -u · sin(θ_approx) + w · cos(θ_approx)
dψ/dt  = yaw_rate_gain · (ψ_cmd - ψ)
du/dt  = (thrust_actual - drag_u · u · |u|) / mass_u
dw/dt  = (-drag_w · w + depth_to_heave_gain · (z_cmd - z) + buoyancy_term) / mass_w
```

其中 `θ_approx` 由目标深度误差经 `pitch_depth_gain` 限幅得到，限幅范围为 `[-max_pitch_rad, +max_pitch_rad]`（默认 ±0.524 rad，即 ±30°）。这一限幅的工程动机是——AUV 实际能够稳定保持的俯仰角受控制权威和水动力恢复力矩约束，超过 ±30° 后舵效非线性显著加剧，预测模型的小角度线性近似就会失效；同时，限幅使"目标深度 → 俯仰角 → 垂向速度"这一派生链条不会因深度误差过大而产生不切实际的瞬时俯仰指令。NED 约定下，深度 z 正向下，俯仰角正为船头向上，因此目标深度更深时需要负俯仰角。推力经 `max(0, T_cmd)` 限幅，确保不产生反向推力——本系统 AUV 主推为单向桨，在物理上不允许负推力。

离散化采用显式 Euler 向前法：

```
X_{k+1} = X_k + dt · f(X_k, U_k)
```

为什么用显式 Euler 而非 RK4 之类的高阶方法？答案来自实时控制的求解时间预算：MPC 控制周期为 100 ms，整个预测时域 2 s 内有 20 步 × 6 维 × 3 维控制 = 360 个变量参与优化，IPOPT 在每次迭代中需要构建并因式分解雅可比矩阵，离散化方案越复杂，单次构建时间越长。RK4 把每步动力学求值次数从 1 次提高到 4 次，对优化问题的雅可比稀疏结构和符号微分时间均有数倍放大效应，对当前的实时性要求是不可接受的。显式 Euler 在 0.1 s 步长下的局部截断误差为 O(dt²)，对 2 s 预测时域内的位置预测误差通常在分米级，已经足够支撑 guidance-level 的参考生成；真正需要精确积分的"低层执行"由 PVS/PID 内层用更短的积分步长完成，无需 MPC 自身承担。其中 `dt` 为 MPC 时间步长（默认 0.1 s），预测时域 `N` 为 20 步，覆盖 2 s 未来状态——这一时域选择同样不是任意的，而是由"百毫秒级一阶执行器惯性需要至少几倍时间常数才能完整反映稳态"反推得出，详见 4.1.1 节关于执行器一阶惯性的讨论。

### 4.4.2 代价函数构建

MPC 在每个控制周期求解以下优化问题：

```
min J = J_tracking + J_control
```

**跟踪代价** `J_tracking`（对预测时域内每步 k = 0…N）：

```
J_tracking = Σ [w_x · (x_k - x_ref_k)² + w_y · (y_k - y_ref_k)²
               + w_z · (z_k - z_ref_k)² + w_ψ · (ψ_k - ψ_ref_k)²
               + w_u · (u_k - u_ref_k)² + w_w · (w_k - w_ref_k)²]
```

跟踪权重的物理含义反映各维度对路径任务的重要性。深度跟踪在近底巡检中权重最大（z 误差直接影响离底安全裕度），航向次之，水平面位置和速度则较为宽松。默认值：`W_x = 1.0, W_y = 1.0, W_z = 5.0, W_ψ = 3.0, W_u = 0.5, W_w = 1.0`。

**控制代价** `J_control`（对控制时域内每步 k = 0…N-1）：

```
J_control = Σ control_scale · [W_ψ_cmd · ψ_cmd_k² + W_z_cmd · z_cmd_k² + W_T · T_cmd_k²]
```

控制代价对指令幅值施加 L2 惩罚，避免输出剧烈波动。`control_scale` 由 UA 机制根据置信度动态调整（详见 4.4.3）。默认权重为：`W_ψ_cmd = 0.1, W_z_cmd = 0.1, W_T = 0.05`。

### 4.4.3 UA-MPC 不确定性感知权重动态调整算法

UA-MPC（Uncertainty-Aware MPC）是本文的核心创新点之一。其核心思想是把感知置信度或协方差变化映射到控制代价权重，使控制器在观测不可靠时自动降低激进程度，在观测可靠时积极跟踪参考路径。

#### （1）跟踪权重的不确定性感知调整

 UA 模式下，跟踪权重根据置信度动态缩放。对 x、y、ψ 维度：

```
w_x = W_x · [1 + (low_conf_scale - 1) · (1 - conf)^α]
w_y = W_y · [1 + (low_conf_scale - 1) · (1 - conf)^α]
w_ψ = W_ψ · [1 + (low_conf_scale - 1) · (1 - conf)^α]
```

         z 维度，放大系数减半：

```
w_z = W_z · [1 + 0.5 · (1 - conf)^α]
```

--------：
- `conf ∈ [0, 1]` 为感知置信度，由 EKF 协方差计算得到
- `low_conf_scale` 为低置信度缩放因子（默认 3.0），控制不确定性最大可放大跟踪权重多少倍
- `α`（`confidence_alpha`）为幂指数（默认 1.5），控制权重随置信度下降的非线性程度。当 `α = 1` 时退化为线性调整

幂函数 `(1 - conf)^α` 确保：置信度高时权重接近基础值；置信度低时权重放大，优化器更倾向于在参考轨迹附近保守跟随，减少偏离。

#### （2）控制代价的 sigmoid 平滑调整

`control_scale` 采用 sigmoid 函数实现平滑过渡：

```
sig = 1 / [1 + exp(k · (conf - confidence_threshold))]
control_scale = low_conf_ctrl_scale + (1 - low_conf_ctrl_scale) · (1 - sig)
```

参数说明：
- `k`（`confidence_smoothness_k`）为 sigmoid 陡峭度（默认 8.0）
- `confidence_threshold` 为置信度阈值（默认 0.6）
- `low_conf_ctrl_scale` 为低置信度控制缩放因子（默认 0.3）

置信度高于阈值时 `control_scale ≈ 1`，控制指令正常输出；置信度低于阈值时 `control_scale` 平滑降至 `low_conf_ctrl_scale`，使优化器对控制量施加更大惩罚，输出更平滑的指令。相比硬切换（hard threshold），sigmoid 平滑避免了权重突变导致的控制量跳变。

#### （3）消融模式开关

UA-MPC 提供 `mpc_mode` 消融开关：
- `mpc_mode = "ua"`：启用完整的 UA 机制（跟踪权重 + 控制代价的动态调整）
- `mpc_mode = "baseline"`：忽略置信度，权重恒定，作为消融对照基线

 `AUV_MPC_MODE` 实现，支持 sweep 实验自动化。

#### （4）UA-MPC 参数完整清单

| 参数 | 默认值 | 含义 | 消融变体 |
|---|---|---|---|
| `mpc_mode` | `ua` | baseline / ua 切换 | A0 vs A1 |
| `low_confidence_scale` | 3.0 | 低置信度跟踪权重放大倍数 | A4（设为 0 退化为 baseline） |
| `low_confidence_control_scale` | 0.3 | 低置信度控制代价缩放 | — |
| `confidence_alpha` | 1.5 | 跟踪权重幂指数 | A3（设为 1.0 退化为线性） |
| `confidence_smoothness_k` | 8.0 | sigmoid 陡峭度 | A2（设为 hard 关闭 sigmoid） |
| `confidence_threshold` | 0.6 | 置信度阈值 | — |
| `prediction_horizon` | 20 | 预测步数 N | — |
| `dt` | 0.1 | 时间步长（s） | — |

### 4.4.4 参考轨迹生成

模型、代价、UA 权重三层确定后，下一个问题是优化器追什么——也就是 MPC 的"参考从哪里来"。在不同任务阶段，参考的来源完全不同：跟踪阶段需要从已知电缆点序列中抽取一段沿路前推的预瞄路径，搜索阶段则没有路由参照、只能由当前航向和深度自行延展。直接把这两类语义压在同一段代码里会让接口臃肿，本系统据此把参考生成分为两种互斥模式，由 `use_los_reference` 开关切换：

1. **LOS 动态模式**（`use_los_reference = true`）：基于电缆点序列和 LOS 前视距离动态生成参考轨迹。算法沿电缆点序列逐步前推，前视距离随时间递增（`los_lookahead += target_speed · dt`），使 MPC 能预瞄前方路径。这种"边走边伸前视"的设计意味着——预测时域内 N 步参考点对应的不是当前 LOS 锚点的"原地复制"，而是沿电缆方向逐步往前的真实路径采样，从而让 MPC 优化器可以同时考虑"当前位置如何修正"和"未来若干步即将面对的弯道"。该模式适用于已经获得稳定电缆路由的跟踪阶段。

2. **恒定航向模式**（`use_los_reference = false`）：使用恒定航向 + 恒定深度的前向推进策略生成参考轨迹。该模式不依赖电缆点先验，完全由当前航向、当前深度和参考速度推算未来 N 步的状态。它在搜索阶段（尚未确认电缆位置）和锁定阶段（电缆位置估计仍在收敛）作为缺省参考，使 MPC 在没有路由信息时仍能工作，而不至于因"参考缺失"而求解失败。

无论哪种模式，最终输出都是一份 `(6, N+1)` 维的参考矩阵，每一列对应一个时间步的 `[x, y, z, ψ, u, w]^T` 期望值，与状态向量的 6 维一一对齐。把参考从"标量序列"扩展到"完整状态序列"是 MPC 的标准做法——它让代价函数可以对每个状态分量单独施加权重，而不是只对一个综合误差求平方，这一点在 4.4.2 节代价函数构建中已经体现。

### 4.4.5 执行器物理饱和约束处理

参考已经准备好之后，下一个问题是优化器可以"在多大范围内"自由选择控制量。MPC 在数学上可以输出任意指令值，但实际执行器有舵角限幅、舵角变化率限制、推力上下限等物理约束——任何超出这些约束的指令在低层都会被强制限幅，反而使 MPC 模型预测和真实执行轨迹脱节。本节按"硬约束 + 速率/带宽扩展约束"两层组织约束体系，前者保证指令"物理可执行"，后者保证指令"工程可平滑"。

**硬约束体系**：

| 约束类型 | 表达式 | 默认范围 | 物理含义 |
|---|---|---|---|
| 航速下限 | `u_k ≥ min_speed` | 0.1 m/s | 确保舵效 |
| ψ_cmd 限幅 | `ψ_cmd ∈ [min_psi_cmd, max_psi_cmd]` | [-π, π] rad | 航向指令合理性 |
| z_cmd 限幅 | `z_cmd ∈ [min_z_cmd, max_z_cmd]` | [0, 50] m | 深度指令合理性 |
| 推力下限 | `T_cmd ≥ min_thrust` | 0% | 防止推力清零失稳 |
| 推力上限 | `T_cmd ≤ max_thrust` | 100% | 执行器饱和 |

硬约束的逐项动机：航速下限来自欠驱动 AUV 的物理事实——舵面通过水流作用力产生力矩，速度太低时舵效近乎为零，控制器再多调整也无法形成有效的转向力，因此把 `u ≥ 0.1 m/s` 作为硬约束是必要的；推力下限设为 0% 而非"任意小负值"则是因为本系统主推为单向桨，物理上不允许反推；深度上限设为 50 m 与本系统设计的最大下潜深度对齐。

**P1 扩展约束**（速率 + 带宽）：

| 约束类型 | 表达式 | 默认值 | 物理含义 |
|---|---|---|---|
| z_cmd 速率 | `|z_cmd_{k+1} - z_cmd_k| ≤ delta_z_max_per_step` | 0.5 m/step | 深度指令变化率 |
| ψ_cmd 速率 | `|ψ_cmd_{k+1} - ψ_cmd_k| ≤ delta_psi_max_per_step` | 8°/step | 航向指令变化率 |
| z_cmd 带宽 | `|z_cmd_k - z_current| ≤ z_band` | 3.0 m | 深度指令不能离当前态太远 |
| ψ_cmd 带宽 | `|ψ_cmd_k - ψ_current| ≤ psi_band` | 45° | 航向指令不能离当前态太远 |

为什么硬约束之外还要再加一层"速率 + 带宽"约束？答案来自实测中观察到的两类不利现象：第一，纯硬约束允许优化器在相邻两步给出相差 30° 的航向指令，这种跳变会让低层 PID 频繁过冲，把"平滑参考"变成"阶跃参考"；第二，优化器可能在某一步给出远离当前态的指令（例如当前深度 5 m，下一步给 25 m 的目标深度），即使在硬约束 [0, 50] m 内合法，但工程上这种"瞬时大步跳"无法被一阶执行器跟随。速率约束限制了相邻步之间的"指令斜率"，带宽约束限制了"任一时刻指令偏离当前态的最大距离"——前者管"短期变化率"，后者管"中期偏离量"，两者一起把优化器的解空间收敛到"内层 PID 能稳定跟随"的窗口内。这两类约束可以分别启用/禁用（`enable_rate_constraints` 和 `enable_band_constraints`），便于消融实验。在 P1 之前的 baseline 仅保留硬约束体系，P1 引入速率与带宽约束后，控制指令更平滑，求解时间略有上升——这一权衡在实验侧由 5 章控制平滑度对比给出量化证据。

### 4.4.6 求解器实现与热启动

约束体系给定后，最后一步是把"如何求解这个非线性优化问题"的工程实现说清楚。MPC 在每个 100 ms 控制周期都要重新求解一次包含 360 个变量的非凸 NLP 问题，求解器选择直接决定整个系统能否跑得动。本系统采用 CasADi Opti 作为符号建模框架、IPOPT 作为后端求解器：CasADi 负责把 Python 写的代价函数和约束自动符号微分得到雅可比，IPOPT 则在每次调用中用内点法迭代求解。

工程实现上有三个关键细节决定能否做到"实时可用"：

- **构建一次、复用多次**：优化问题的整体结构（变量数量、约束类型、雅可比稀疏模式）在 MPC 配置确定后就固定，不再随时间变化。本系统据此把 IPOPT 求解器结构在初始化时编译一次（`_build_solver`），运行期反复求解时仅用 `set_value` 更新参考、当前状态、置信度等参数值，避免每次都重复符号微分和编译。这一优化把单次求解时间从秒级压缩到几十毫秒级，使 100 ms 控制周期变得可实现。
- **热启动**（Warm Start）：使用上一次最优控制序列作为初始猜测，加速 IPOPT 收敛。热启动序列通过右移实现：`U_guess[:, k] = U_prev[:, k+1]`，最后一步重复使用上一步最后一个控制量。"右移"的物理含义是——上一周期的预测时域已经覆盖了 [t, t+2s]，这一周期需要 [t+0.1s, t+2.1s]，二者只相差一步，把上一次解整体平移一步作为猜测，IPOPT 通常在 5–10 次迭代内即可收敛，相比冷启动（30–50 次迭代）节省一个数量级的计算时间。
- **求解失败的兜底**：当 IPOPT 返回失败状态时（求解超时、约束不可行、迭代发散），求解层抛出 `RuntimeError`。在 `MPCController` 层捕获异常后，根据 `fail_safe_fallback` 配置决定是否回退到上一次输出或直接返回设定点——前者维持指令连续性、后者退化为开环控制。这一回退路径是行为树 4.2.3 节"控制器异常 → 回退到 PID baseline"应急规则的实际接入点。

求解器配置为 `ipopt.tol = 1e-4`、`ipopt.max_iter = 100`、`print_level = 0`：容差 1e-4 在 MPC 这种"快速迭代+持续修正"的场景下足够，过低的容差只会延长求解时间；最大迭代次数 100 是软性上限，配合上述热启动机制实际平均迭代次数远小于此；输出级别 0 是为了不污染 ROS2 日志。在 PVS 仿真侧，舵角限幅为 ±5°–±6°（在 PVS `depthHeadingAutopilot` 侧实现），角速度限制由 MPC 变体的 `psi_band_deg` 参数控制，推力下限由 `min_thrust` 参数约束——这三层限幅互为冗余：MPC 优化器内部限幅 + MPC 输出后限幅 + PVS 内层再限幅，确保任何一层失效都不会让超界指令穿透到执行器。

## 4.5 决策与控制系统的鲁棒性分析

前面四节给出了任务调度、轨迹生成、UA-MPC 控制和约束体系四个层面的完整设计，但工程上还需要回答最后一个问题——这套设计在"非理想条件"下能否守住底线？所谓"非理想条件"包含两类：一是慢变退化，例如感知质量在长时间任务中持续抖动、海流扰动叠加、地形起伏比预设强烈；二是快变冲击，例如电缆突然进入掩埋段、AUV 在拐点附近遭遇横向流场、声呐通道短时完全失效。对这两类条件分别给出鲁棒性证据，是验证分层架构可工程化的关键一步。本节据此把鲁棒性证据组织为两条线：4.5.1 节按"三层证据"自下而上展开（近底安全 → 复杂路径 → 不确定性适应），论证不同控制层级各自的能力上界；4.5.2 节按"极端工况边界"自外而内收紧（六类极端电缆巡检场景），论证哪些场景已经超出当前架构的能力，必须由安全回退路径接管。

### 4.5.1 感知信号剧烈波动下的控制平滑度对比

本节按"近底安全 → 复杂路径 → 不确定性场景"三个层次组织鲁棒性证据，逐层说明分层控制架构在哪些条件下成立、在哪些条件下需要回退。这一组织顺序背后的逻辑是——任何复杂控制器在用之前都必须先满足"不撞地"，再讨论"路径精度"，最后才谈"在不确定环境下还能不能保持精度"。把三个层次按由低到高排列，可以让读者清晰看到每一层证据各自支撑哪一类工程结论，避免把"近底安全已证明"误读为"所有工况下控制器都已证明"。

**第一层：terrain-following 的近底安全性**。已有 terrain benchmark 支撑。PID terrain 在 60 s 真口径正式结果（`results/control/terrain_following_20260619_222639/`）中实现了 `seabed_clearance_rmse_to_3m ≈ 1.14 m`、四相 clearance 随真地形起伏，三档 low/mid/high terrain 消融均无 `<1.5 m` 安全违规（早先 `0.1752 m` 系分析层 datum bug 假象，已被真口径重跑取代，溯源见 [docs/thesis/08_terrain_following_pid_mpc_status.md](file:///home/auv_user/auv_ws/AUV-Master-Project/docs/thesis/08_terrain_following_pid_mpc_status.md) §8.1/§8.2）。MPC terrain 虽然改善了固定深度 baseline，但未超过调优后的 PID/PVS。这一结果意味着——在"恒定离底高度"这一最基础的近底安全任务上，调优良好的 PID/PVS 内层已经把贴底误差压到米级以内，外层加 MPC 只是锦上添花、并没有打开新的能力维度。其工程归因在于 PVS `depthHeadingAutopilot` 内置的深度 PID 直接控制水平舵的瞬态响应，相比 MPC guidance-level 通过"目标深度参考 + 内层 PID 跟随"的两级链路，缺少一级延迟，对地形起伏的响应更直接。换言之，当任务的本质是"快速贴地"而非"复杂预瞄"时，MPC 的优势区被显著压缩。

**第二层：复杂平面路径制导**。已有离线 MPC x/y/yaw 支线提供初步证据。公平口径重跑（`/auv_data/results/control/mpc_xy_yaw_extreme/20260620_011831/`）显示，MPC 在长波/短波 S 弯与 hairpin 上的横向误差优于或持平 yaw-only PID 与 LOS 强 baseline，仅在直角 chicane 上 LOS 前瞻更优（溯源见 doc 08 §8.7，早先"未全面超过 LOS"的判断源自 harness `+2.0 m` 偏置 bug，修复后已推翻）。这一结果在工程上传达两层信息：一方面，"预瞄能力"的确把急转弯和折返路径上的横向误差压低了一个量级——这与 MPC 在预测时域内能"看到下一段曲率"而 yaw-only PID "只能看到当前误差"的本质差异相符；另一方面，LOS 制导本身已经包含了某种程度的"几何前视"（前视距离 + 投影到电缆的横向偏差），使得它在路径几何相对规则（如分段直线的直角 chicane）的场景下仍占优。本系统的策略由此明确——把 MPC 主要用于"LOS 不擅长"的不规则曲率路径预瞄，而不是把 MPC 当作"LOS 替代品"全面铺开。

**第三层：高不确定性场景下的 UA-MPC 主消融**。目前已完成 3 场景 × 2 模式 × 3 seed 的主消融实验，涵盖 baseline、DVL dropout 60% 和 combined stress 场景。在 baseline 和 combined stress 场景中，UA-MPC 相比 baseline-MPC 在定位指标上展现出改善趋势，但在 DVL dropout 60% 的极重度丢包场景中优势不显著，说明 EKF 在极重度速度观测丢失下状态质量已严重退化，MPC 权重调整难以补偿。这一对比给出的工程启示是——UA-MPC 的核心机制是"在感知质量变化时调整代价权重"，但前提是 EKF 输出的状态估计本身仍然有意义；当 DVL 丢包率达到 60%以上、ES-EKF 已经退化为接近"纯惯性递推"时，无论 MPC 如何调权重，输入到 MPC 的状态本身已经失去了校正力，控制层不可能凭"权重调整"独自修复"感知崩溃"。这恰好印证了第 3 章建立的"感知不确定性必须沿层向上传递"的整体观点：UA-MPC 是这条链路的下游环节，但不是它的最后兜底，最后兜底必须由 4.2.3 节定义的行为树应急规则承担。

### 4.5.2 极端工况下的安全性边界测试

4.5.1 节的三层证据回答了"常规工况下分层架构如何工作"，但工程验收还需要回答另一类更尖锐的问题——"极端工况下分层架构在哪个边界失效，该失效是否被安全回退路径接住？"为什么极端工况必须单独考虑、而不能与常规消融场景合并？原因有两条：第一，极端工况的物理风险量级与常规场景不同——常规场景下 MPC 性能下降表现为"横向误差扩大几十厘米"，而极端工况下相同性能下降可能直接导致"撞地、绕远、丢失目标"等不可逆后果；第二，极端工况之间的叠加效应不可忽略——单独的"急转弯"或单独的"横向流"都可被 MPC 的预瞄/容差吸收，但二者同时出现时其耦合行为往往不在任何单一消融场景的覆盖范围内。基于这两点，极端工况必须按"物理风险类别 + 是否触发安全回退"两个维度单独建模。

当前已有 MPC x/y/yaw 支线中的 `chicane_90deg` 和 `hairpin_180deg` 极端路径，但尚未接入完整 PVS/ROS 感知闭环——这意味着"路径几何极端性"已经被部分量化，但"几何极端 + 感知退化"组合工况仍属待补实验。

`pvs_extreme_cable_scenarios.md` 中定义了 6 个极端电缆巡检场景：S-curve、Hairpin、Slope Crossing、Buried Gap、Cross Current 和 Combined Extreme，每个场景包含真实风险分析、路径设置、观测角色和评价指标。这 6 个场景按物理风险归类如下：S-curve 与 Hairpin 测试"几何曲率极端"对预瞄能力的边界；Slope Crossing 测试"水平+垂直耦合"对 4-DOF 简化模型的边界；Buried Gap 测试"磁信号瞬时丢失"对感知-控制接力的边界；Cross Current 测试"持续横向力"对欠驱动控制的边界；Combined Extreme 把上述四类同时叠加，专门用于检验安全回退路径是否被"高优先级 Selector 子树"按设计触发。每个场景都对应一组消融模式启用/禁用对照——例如 Buried Gap 场景下需对比 UA-MPC 启用与禁用时控制平滑度，Cross Current 场景下需对比速率/带宽约束启用与禁用时航向跳变次数——通过这种"场景 × 模式"的二维设计，可以把单一极端因素的影响与多因素耦合的影响分别隔离出来。

> **表格占位符**：正式论文中需补充极端工况下的控制平滑度对比表，包括控制量变化率、求解时间分布、fallback 触发率和安全违规次数。

## 4.6 本章小结

本章围绕"AUV 海缆巡检该用什么样的决策与控制结构"这一问题，按"约束 → 调度 → 轨迹 → 控制 → 鲁棒性"五个层次完成了完整设计：4.1 节先回答欠驱动 AUV 的运动约束和分层解耦的工程动机，把"任务调度、轨迹生成、参考生成、低层执行、安全仲裁"五类语义负载明确分层；4.2 节据此给出基于行为树的任务调度方案，论证了 Selector + Sequence 抢占式优先级相对 FSM 在"故障可组合、应急可插入"上的根本优势，并把巡检流程切成"搜索 → 锁定 → 跟踪 → 异常处理"四阶段；4.3 节回答了几何路径与速度规划，把之字形扫描和感知置信度驱动的动态航速联系起来；4.4 节作为本章主线，按"模型 → 代价 → UA 权重 → 参考 → 约束 → 求解器"六层展开 UA-MPC 的完整实现，重点阐述了 (1-conf)^α 跟踪权重 + sigmoid 平滑控制代价的 UA 机制、LOS 动态与恒定航向两种参考模式的互斥设计、速率与带宽两类扩展约束的工程必要性、CasADi+IPOPT 热启动求解的实时可用性；4.5 节最后给出三层鲁棒性证据和六类极端工况边界，明确了当前各控制层级的能力上界。

从证据等级看，本章可以稳妥支撑的结论有三条：**第一，行为树相对 FSM 的可扩展性优势在单次基准实验中可见，但仍缺乏多场景统计**；**第二，PID/PVS 在 terrain following 主任务上是当前最可靠的近底地形跟随主控制器，米级以内离底误差和零安全违规已在多档地形消融中验证（真口径，见 §4.5.1）**；**第三，UA-MPC 在 baseline 和 combined stress 场景下相对 baseline-MPC 展现定位改善趋势，但在感知严重退化（DVL 丢包 60%）的场景下优势不显著，说明感知不确定性的处理必须由 EKF/UA-MPC/行为树三层共同承担**。本章不能支撑的结论同样需要明确——"MPC 全面优于 PID/LOS"不成立，"UA-MPC 单独可应对所有不确定性场景"不成立，"极端工况下分层架构必然安全"亦未在 PVS 完整闭环下验证，需要等待 4.5.2 节列出的六个极端电缆巡检场景在第 5 章实验侧给出多 seed 统计。

把这些结论合在一起看，本章给出的不是"一个万能控制器"，而是"一套分层控制与安全回退框架"——其工程价值不在于让某一层控制器跑得最优，而在于让"任务调度、参考生成、低层执行、安全仲裁"四个职责彼此独立验证、独立替换、独立兜底。这一框架将在第 5 章被进一步置于真实实验工况下检验，并作为后续硬件部署阶段的算法基线。
