# auv_bridge 仲裁器长期路线图

本文档用于固化 auv_bridge 仲裁器的长期实施基线，避免后续跨会话推进时出现要求遗漏、实现顺序错乱或协议语义漂移。

当前目标不是一次性重写桥接链路，而是在保持现有 `$CKTH` 72B 下行、`$AUV` 145B 上行、现有 ROS2 栈入口和 Python 上位机主通信链路兼容的前提下，逐步加入手控/自主仲裁、自主安全握手、双路 telemetry、抓包与联调能力。

## 1. 已冻结的设计决定

- `REQ_AUTO` 通过 `rt/pc/cmd_raw` 原始 72B 报文路径表达，不新增独立请求 topic。
- Jetson 自主控制输入使用新增 ROS2 自定义消息 `MpcCmd.msg`，不复用 `geometry_msgs/Twist`。
- `DENY_REASON` 与 `Active_Arbiter` 第一阶段只出现在 bridge 发布的解包后 Zenoh telemetry 中，不写回 145B `$AUV` 原始二进制。
- Zenoh 键名继续沿用 `rt/` 命名体系。
- `$CKTH` 舵角 on-wire 编码保持当前 0.1 度 `int16`，不切换到 `0-4095`。
- 手动优先抢占与 Jetson 心跳超时归零属于 P0 安全要求，不能后置。

## 2. 长期架构边界

- [common/protocol.py](../common/protocol.py) 是协议字段、键名、编解码辅助的唯一事实源。
- [common/enums.py](../common/enums.py) 是工作模式、仲裁模式、拒绝原因等状态语义的唯一事实源。
- [brain_linux/src/auv_bridge/auv_bridge/bridge_node.py](../brain_linux/src/auv_bridge/auv_bridge/bridge_node.py) 只负责输入接入、规范化、调用仲裁与发布，不承载协议常量真值表。
- `arbiter.py` 与 `autonomy_guard.py` 必须保持“纯内核”属性，不依赖 ROS2、Zenoh 或 socket。
- [Console上位机软件/auv_console_python](../../Console上位机软件/auv_console_python) 现有 UDP/串口通信主链保持不动，Zenoh 只作为新增 side channel。
- [sim_holoocean/interfaces/mock_amd_server.py](../sim_holoocean/interfaces/mock_amd_server.py) 与未来 `scripts/sniffer.py` 只复用 shared protocol 解析，不各自维护私有字段解释。

## 3. 要求映射矩阵

| 要求 | 核心落点 | 第一阶段验收口径 |
| --- | --- | --- |
| 手控透传 | `common/protocol.py`、`arbiter.py`、`bridge_node.py` | `0x01` 模式下 raw `$CKTH` 透传到 AMD |
| 自主接管 | `MpcCmd.msg`、`arbiter.py` | `0xEE` 时由 MPC 覆盖电机与四舵角 |
| 手动优先抢占 | `arbiter.py` | 收到 `0x02` 或 `0x91` 立即回 Remote |
| Jetson 心跳超时保底 | `arbiter.py`、配置 YAML | 自主模式超时大于 0.5s 时四舵归正、推力归零 |
| 自主安全握手 | `autonomy_guard.py`、`common/enums.py` | 不满足条件时返回 `DENY_REASON` 且不切 ACTIVE |
| 双路 telemetry | `bridge_backends.py`、`bridge_node.py` | 同时发布 `rt/auv/telemetry` 与 `rt/auv/viz/internal` |
| 上位机拒绝反馈 | Python 上位机 side channel | UI 可见拒绝原因与当前仲裁状态 |
| 协议抓包与彩色日志 | `mock_amd_server.py`、`scripts/sniffer.py` | 能记录原始十六进制与解包结果 |

## 4. 分阶段实施路线

### Phase 0: 契约冻结

目标：把需求和边界写清楚，避免后续代码先行导致语义漂移。

要做的事：

- 维护本路线图，确保要求矩阵、冻结决定、验收口径可追踪。
- 明确第一阶段不做项：145B `$AUV` 改包、舵角编码重定义、上位机主通信链替换。
- 所有后续阶段都先改 shared contract，再改 bridge 运行时。

### Phase 1: Shared Contract

目标：先统一共享语义，再进入实现。

主要文件：

- [common/enums.py](../common/enums.py)
- [common/protocol.py](../common/protocol.py)

要做的事：

- 新增 `AUTO_STATE`、`ArbiterMode`、`ArbiterSource`、`DenyReason` 等共享状态语义。
- 新增或固化 `rt/pc/cmd_raw`、`rt/auv/telemetry`、`rt/auv/viz/internal` 等路径常量。
- 补齐 raw `$CKTH` 到标准 dict、标准控制量到 `$CKTH`、`$AUV` 到 bridge telemetry payload 的 helper。
- 保证与现有 Python 上位机、Mock AMD、protocol_udp 闭环兼容。

阶段完成条件：

- shared contract 可独立被 bridge、mock、sniffer、上位机复用。
- 不修改现有 145B 上行包格式。

### Phase 2: ROS2 边界消息

目标：把 Jetson 自主输入从 transport 细节中解耦出来。

主要文件：

- `brain_linux/src/auv_interfaces/msg/MpcCmd.msg`
- 相关 `CMakeLists.txt`、`package.xml`

要做的事：

- 更新 `auv_interfaces` 构建与依赖。

阶段完成条件：

- bridge 可通过明确消息接收自主控制量。
- 后续 MPC 算法升级不需要回改 raw 协议解析。

### Phase 3: Arbiter Core

目标：实现独立、可单测的仲裁状态机。

主要文件：

- `brain_linux/src/auv_bridge/auv_bridge/arbiter.py`

要做的事：

- 维护当前模式、最新手控 raw 命令、最新 `MpcCmd`、最新心跳时间。
- Remote 模式下原样透传 `cmd_raw`。
- Autonomous 模式下保留 raw 包辅助位，只覆盖四舵角和推力，并强制 `work_instruct=0xEE`。
- 收到 `0x02` 或 `0x91` 时立即切回 Remote。
- 自主模式心跳超时大于 0.5s 时输出保底控制。

阶段完成条件：

- 在不启动 ROS2/Zenoh 的情况下，可通过纯 Python 单元测试验证状态转移和输出封装。

### Phase 4: Autonomy Guard

目标：把“是否允许自主接管”与“接管后如何出控制”拆开。

主要文件：

- `autonomy_guard.py`
- `common/enums.py`

要做的事：

- 实现 `LOCKED/REQUESTING/ACTIVE/DENIED` 状态。
- 检查漏水、总电压大于 47V、置信度大于 0.5、AMD 上行延迟小于 200ms。
- 拒绝时返回精确 `DENY_REASON`。
- 保持 guard 逻辑独立于 bridge backend。

阶段完成条件：

- 自主接管请求有明确放行与拒绝路径。
- 拒绝原因可被 bridge telemetry 发布给上位机。

### Phase 5: Bridge Runtime 接线

目标：把 shared contract、arbiter、guard 接入现有桥接节点。

主要文件：

- [brain_linux/src/auv_bridge/auv_bridge/bridge_node.py](../brain_linux/src/auv_bridge/auv_bridge/bridge_node.py)
- [brain_linux/src/auv_bridge/auv_bridge/bridge_backends.py](../brain_linux/src/auv_bridge/auv_bridge/bridge_backends.py)

要做的事：

- 订阅 `rt/pc/cmd_raw`。
- 订阅 `/auv/control/mpc_cmd`。
- 用 arbiter/guard 输出统一的下行控制报文。
- 发布 `rt/auv/telemetry` 与 `rt/auv/viz/internal` 两路 telemetry。
- 将 freshness、当前模式、拒绝原因等状态注入 telemetry payload。

阶段完成条件：

- topic backend 与 protocol backend 都能运行。
- backend 不承载状态机，状态机只存在于 bridge 内核。

### Phase 6: Config / Launch / Profile

目标：让仲裁功能可切换、可复现、可区分仿真与实物配置。

主要文件：

- [brain_linux/config/params.yaml](../brain_linux/config/params.yaml)
- [config/bridge_params.yaml](../config/bridge_params.yaml)
- 新 launch 文件

要做的事：

- 新增 arbiter enabled、guard thresholds、heartbeat timeout、telemetry keys 等配置。

## 5. 未来需要继续解耦和预留的点

- 协议层预留 schema version 或 metadata hook，但第一阶段不启用。
- Arbiter 与 Guard 保持双内核，不收敛成一个大类。
- backend 只做 transport，不定义控制语义。
- Python 上位机的 Zenoh 扩展必须停留在 communication 层边界，避免 UI 与 transport 紧耦合。
- Sniffer、Mock AMD、Bridge 都必须复用 shared protocol helper，不能各自复制字段映射。
- Launch 与 YAML 按 profile 管理，后续海试、回放、仿真不要继续手改单文件。
