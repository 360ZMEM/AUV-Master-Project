# AUV_Master_Project 原理说明

## 1. 项目目标
本仓库的目标是把原本分散的两套代码逐步收敛成一个可持续演进的 AUV 联合开发仓库：
- 仿真侧：HoloOcean + Zenoh 桥接
- 决策侧：Linux ROS2 Humble 工作区
- 共享层：common 协议、枚举与物理常量

核心原则是：**先统一数据契约，再统一启动方式，最后统一联调流程**。

## 2. 当前仓库的分层图

```text
AUV_Master_Project/
├── common/          # 双端共享契约
├── algorithm/       # 与环境无关的算法
├── config/          # 仿真、桥接、覆盖配置
├── sim_holoocean/   # 仿真与桥接（身体层）
├── brain_linux/     # Linux ROS2 决策工作区（大脑层）
├── msgs/            # 中间件无关的消息映射说明
├── scripts/         # 启动与检查脚本
└── docs/            # 原理说明、开发进度、后续可扩展文档
```

这不是单纯的目录改名，而是把“责任边界”显式化，方便后续逐步替换底层实现而不改上层契约。

## 3. 分层原则

### 3.1 common：单一数据契约源
`common/` 保存所有跨模块共享的“基本法”：
- topic 路径
- JSON 键名
- 行为状态枚举
- 故障码
- 物理常量和限幅
- 通信边界校验函数

这样做的目的，是避免仿真侧和 ROS2 侧各自定义一套字段，导致后面联调时出现“能跑但语义不一致”的问题。

### 3.2 sim_holoocean：仿真与桥接
`sim_holoocean/` 只保留和 HoloOcean 强相关的内容：
- 环境初始化
- 传感器读取
- 坐标系转换
- 物理感知模型
- Zenoh 发布/订阅
- 仿真侧安全与命令防护

这里不放决策逻辑，避免把“看见什么”和“决定做什么”混在一起。

### 3.3 brain_linux：Linux 决策工作区
`brain_linux/` 是 Linux 端 ROS2 工作区：
- `auv_interfaces` 负责消息定义
- `auv_decision` 负责行为决策
- `auv_control` 负责高层控制
- `auv_example` 负责调试入口
- `auv_foxglove` 负责可视化资源
- `auv_bridge` 预留给后续中间件适配

这里不直接调用 HoloOcean API，只通过协议和消息通信。

### 3.4 algorithm：环境无关算法层
`algorithm/` 放与环境无关的算法，例如 PID、导引、轨迹、滤波等。它的特征是：
- 可以脱离仿真单独测试
- 不依赖 ROS2
- 不依赖 HoloOcean

这样做便于复用，也便于后面替换底层环境。

## 4. 数据闭环原理
当前推荐的数据流是：

HoloOcean 仿真 -> 仿真侧传感打包 -> Zenoh topic 发布 -> Linux 决策端订阅 -> 行为树/控制输出 -> 再回到仿真侧执行

其中：
- `common/protocol.py` 负责统一 topic 与键名
- `common/enums.py` 负责统一状态与故障语义
- `common/physics.py` 负责统一物理常量与限幅
- `sim_holoocean/interfaces/holoocean_physics_bridge.py` 负责把原始仿真数据转成统一消息
- `brain_linux/src` 中的 ROS2 包负责消费消息并输出控制目标

### 4.1 当前已经打通的部分
- HoloOcean 仿真侧可以把状态和传感数据包装为统一 JSON
- Zenoh topic 常量已经统一到 `common/protocol.py`
- Linux 决策端目录已经迁入 `brain_linux/src`
- Linux 端启动脚本已经可以 build 和启动 ROS2 包

### 4.2 当前还没有打通的部分
- `auv_bridge` 的正式业务实现
- HoloOcean 与 Linux 决策端的实时闭环联动
- 仿真输出与决策输入之间的正式 DDS/Zenoh 适配层
- 端到端控制回路的正式验收脚本

这意味着：现在已经有“桥接骨架”和“单侧可运行能力”，但还不是“真正的双端闭环系统”。

## 5. 双平台策略
历史上仿真主要在 Windows 跑，决策端在 Windows 上也曾单独存在。现在采用“双平台兼容”策略：
- Linux 是当前主开发环境
- Windows 仍保留可用脚本
- 关键入口统一通过 `scripts/` 启动

这保证了迁移过程中不会一次性切断旧流程。

## 6. 迁移映射关系

### 6.1 仿真侧来源
原 `Master毕业设计代码实现/auv_project_new/AUV_Software_Stack/` 中的内容，已经按新目录重塑到：
- `sim_holoocean/apps`
- `sim_holoocean/interfaces`
- `sim_holoocean/behavior`
- `sim_holoocean/experiments`
- `algorithm`
- `config`

### 6.2 决策侧来源
原 `Console上位机软件/ros2_ws/src/` 中的内容，已经迁入：
- `brain_linux/src/auv_interfaces`
- `brain_linux/src/auv_decision`
- `brain_linux/src/auv_control`
- `brain_linux/src/auv_example`
- `brain_linux/src/auv_foxglove`

### 6.3 当前迁移原则
- 先保持旧入口可运行
- 再增加新入口与新目录
- 最后再收敛旧路径

## 7. 阶段化实施顺序
推荐顺序如下：
1. 统一 common 契约
2. 重塑仿真侧目录与入口
3. 迁移 Linux 决策侧目录
4. 建立等价性验证脚本
5. 再逐步补齐真正的桥接闭环

## 8. 本仓库的关键约束
- 不把决策逻辑塞进仿真层
- 不把 HoloOcean API 塞进 ROS2 层
- 通信边界必须做字段与类型校验
- 标准约束要可追溯到 DLT 1278 等文档
- 新代码优先保持可替换、可回滚、可分层

## 9. 与标准文档的关系
涉及巡检任务定义、告警策略、轨迹策略时，要把设计与标准建立映射关系，而不是只看代码能不能跑。当前要求是：
- 标准引用要写清楚文件路径
- 实现约束要写清楚影响范围
- 改动结果要写清楚验证方式

建议优先参考：
- `标准文档/DLT+1278—2025+海底电力电缆运行规程.pdf`
- `标准文档/《海底电缆巡检运维管理规范》 - 道客巴巴.pdf`
- `标准文档/Analysis+on+Selection+of+Submarine+Cable+Detection+Technology.pdf`

## 10. 当前最重要的结论
现在的仓库已经不是两个孤立代码库的简单拼接，而是在向一个统一的 AUV 联合开发平台演进：
- `common` 定义规则
- `sim_holoocean` 提供身体和感知
- `brain_linux` 提供大脑和决策
- `scripts` 提供统一启动方式

后续工作重点是把桥接链路真正闭环起来，而不是继续堆新的孤立脚本。
