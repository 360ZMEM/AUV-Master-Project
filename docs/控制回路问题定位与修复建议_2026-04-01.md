# 控制回路问题定位与修复建议

本文档回答三个问题：

1. 目前问题出在哪里。
2. 这些问题和哪些参数或结构有关。
3. 可能的修复点在哪里。

## 1. 目前问题出在哪里

### 1.1 问题不在协议链路

本轮 protocol_udp 联调已经证明闭环链路是通的：

- ROS2 侧能收到 `/auv/sensors/depth` 与 `/auv/state/filtered`。
- 决策层能发布 `/auv/control/setpoint`。
- 控制器能发布 `/cmd_vel`。
- sim 侧 Mock AMD 已持续收到非零命令，例如：

```text
cmd=(-28.5,-30.0,28.5,30.0,12.1)
```

因此，当前问题是控制回路质量问题，不是 protocol_udp 传输问题。

### 1.2 当前现象

本轮联调抓到的实时样本如下：

- `/auv/control/setpoint`
  - `mode = ZIGZAG_SEARCH`
  - `target_depth_m = 4.0`
  - `target_heading_rad = 0.0`
  - `target_speed_mps = 0.4`
- `/auv/diagnostics`
  - `depth_m = 3.302`
  - `target_depth_m = 4.0`
  - `depth_error_m = -0.698`
  - `speed_mps = 0.4002`
  - `target_speed_mps = 0.4`
- `/cmd_vel`
  - `linear.x = 13.9`
  - 四片舵面基本打到 `±30 deg`

这说明三个事实：

1. 速度环已经基本贴住目标，速度不是当前主矛盾。
2. 深度还存在约 `0.7 m` 的稳态误差。
3. 在这种误差量级下，舵面却长期接近饱和，说明控制分配或目标定义存在结构性问题。

### 1.3 结构性根因 1：行为树没有提供动态航向目标

[brain_linux/src/auv_decision/auv_decision_core/models.py](../brain_linux/src/auv_decision/auv_decision_core/models.py) 中的 `MotionGoal` 只有：

- `target_depth_m`
- `target_speed_mps`
- `sine_amplitude`
- `sine_period_s`

它并没有 `target_heading_rad` 字段。

而 [brain_linux/src/auv_control/auv_decision_ros/mappers.py](../brain_linux/src/auv_control/auv_decision_ros/mappers.py) 在生成 `Setpoint` 时，会把缺省航向写成：

```python
msg.target_heading_rad = float(goal.get('target_heading_rad', 0.0))
```

这意味着当前决策层没有显式输出航向时，控制器永远拿 `0 rad` 当目标航向。

本轮联调里，实时姿态换算得到当前 `yaw ≈ 132.7 deg`，但目标仍是 `0 deg`。这会让 yaw 环持续认为自己存在大角度误差，导致方向舵长期打满。

结论：当前偏航饱和首先是“目标定义缺失”，不是简单的 PID 参数过大。

### 1.4 结构性根因 2：姿态角速度反馈不足

[algorithm/auv_pid_controller.py](../algorithm/auv_pid_controller.py) 中：

- pitch 环微分项使用 `q`
- yaw 环微分项使用 `r`

但本轮 `/auv/state/filtered` 样本里：

- `twist.twist.angular.x = 0.0`
- `twist.twist.angular.y = 0.0`
- `twist.twist.angular.z = 0.0`

这意味着控制器虽然写了微分阻尼，但当前反馈链路实际上没有给到有效角速度，等价于 pitch/yaw 的阻尼能力被大幅削弱。

结论：就算不改任何 PID 参数，只要角速度反馈缺失，舵面饱和和超调风险也会明显变大。

### 1.5 结构性根因 3：深度环和偏航环共享舵面，但没有优先级分配

[algorithm/auv_pid_controller.py](../algorithm/auv_pid_controller.py) 当前做法是：

- 深度外环先生成 `target_pitch`
- pitch 环生成一组 elevator 命令
- yaw 环生成一组 rudder 命令
- 最终直接写入四个舵面

当 yaw 环已经因为错误航向目标打满时，depth/pitch 环再想修正深度，实际可用控制裕度就很有限。结果表现就是：

- 深度误差不算特别大
- 但舵面已经接近极限
- 控制器没有进一步的分配策略去决定“谁优先”

结论：这不是单一 PID 数值问题，而是控制分配层还比较原始。

## 2. 这些问题和什么参数有关系

### 2.1 与目标定义有关的参数和代码

直接相关：

- [brain_linux/src/auv_decision/auv_decision_core/behaviors.py](../brain_linux/src/auv_decision/auv_decision_core/behaviors.py)
  - `DiveToDepth.target_depth_m = 4.0`
  - `ParallelTracking.target_speed_mps = 0.6`
  - `ZigZagSearch.target_speed_mps = 0.4`
- [brain_linux/src/auv_decision/auv_decision_core/models.py](../brain_linux/src/auv_decision/auv_decision_core/models.py)
  - 当前 `MotionGoal` 缺少 `target_heading_rad`
- [brain_linux/src/auv_control/auv_decision_ros/mappers.py](../brain_linux/src/auv_control/auv_decision_ros/mappers.py)
  - `target_heading_rad` 缺省值是 `0.0`

判断：这些不是“调参项”，而是当前最关键的结构缺口。

### 2.2 与深度/姿态控制有关的参数

集中在 [brain_linux/config/params.yaml](../brain_linux/config/params.yaml)：

- `control.depth.kp/ki/kd`
- `control.depth.target_pitch_deg_max`
- `control.depth.target_pitch_rate_limit_deg_s`
- `control.pitch.kp/ki/kd`
- `control.yaw.kp/ki/kd`
- `control.feedforward_trim_deg`

其中优先级排序建议如下：

1. `control.depth.target_pitch_deg_max`
2. `control.pitch.kp` / `control.pitch.kd`
3. `control.yaw.kp` / `control.yaw.kd`
4. `control.depth.kp` / `control.depth.ki`

原因：当前最明显的问题不是“速度不够”，而是姿态和航向相关舵面过于容易顶到限幅。

### 2.3 与推进/速度有关的参数

仍在 [brain_linux/config/params.yaml](../brain_linux/config/params.yaml)：

- `control.target_u`
- `control.u0`
- `control.u_min`
- `control.speed.kp/ki/kd`
- `control.speed.feedforward.a/b/c`

但要注意：这轮观测里 `speed_mps ≈ 0.4002`，已经非常贴近 `target_speed_mps = 0.4`。因此这些参数不是当前第一修复优先级。

### 2.4 与协议映射/执行器尺度有关的参数

分别在：

- [brain_linux/config/params.yaml](../brain_linux/config/params.yaml)
  - `bridge.protocol_udp.main_motor_rpm_scale`
- [config/bridge_params.protocol_udp.yaml](../config/bridge_params.protocol_udp.yaml)
  - `bridge.protocol_udp.main_motor_rpm_scale`
  - `bridge.fin_abs_max`
  - `bridge.thrust_min`
  - `bridge.thrust_max`

这些参数决定协议值与仿真执行器量纲之间的映射关系。

判断：它们会影响“同样一个 thrust_cmd 在协议层到底被解释成多大的推进量”，但从当前现象看，主问题仍然是航向目标缺失和舵面饱和，而不是 RPM 标度设置错了。

### 2.5 与反馈质量有关的参数或模块

与参数相比，更关键的是模块输出：

- [brain_linux/src/auv_localization/auv_localization/auv_localization_node.py](../brain_linux/src/auv_localization/auv_localization/auv_localization_node.py)
- [brain_linux/src/auv_bridge/auv_bridge/bridge_node.py](../brain_linux/src/auv_bridge/auv_bridge/bridge_node.py)

需要确认：

1. IMU 角速度是否进入了 localization。
2. localization 发布的 `Odometry.twist.twist.angular.*` 是否应该为非零。
3. protocol uplink 当前是否只提供了姿态，没有提供足够的角速率信息。

## 3. 可能的修复点在哪里

### 3.1 第一优先级：补齐 guidance/heading 闭环

这是当前最重要的修复点。

建议：

1. 在 [brain_linux/src/auv_decision/auv_decision_core/models.py](../brain_linux/src/auv_decision/auv_decision_core/models.py) 的 `MotionGoal` 中增加 `target_heading_rad`。
2. 在 [brain_linux/src/auv_decision/auv_decision_core/behaviors.py](../brain_linux/src/auv_decision/auv_decision_core/behaviors.py) 或 guidance 层生成实际航向目标，而不是让 `Setpoint` 默认回退到 `0.0`。
3. 如果暂时还没有完整 guidance，可先做一个保守过渡方案：进入某个任务模式时，把当前 yaw 锁存为 heading hold 目标，而不是强制目标为北向 `0 rad`。

如果这一项不做，后面即使继续调 `yaw.kp`，也只是把结构问题变得“没那么明显”，并没有真正解决。

### 3.2 第二优先级：恢复或补齐角速度反馈

建议检查并修复：

1. [brain_linux/src/auv_bridge/auv_bridge/bridge_node.py](../brain_linux/src/auv_bridge/auv_bridge/bridge_node.py) 是否把 IMU 角速度完整发布到 ROS2。
2. [brain_linux/src/auv_localization/auv_localization/auv_localization_node.py](../brain_linux/src/auv_localization/auv_localization/auv_localization_node.py) 是否把角速度写入 `Odometry.twist.twist.angular`。
3. 如果 EKF 当前不估计角速度，至少先在 controller 中临时直接使用 IMU 角速度订阅，避免 pitch/yaw 的微分项失效。

### 3.3 第三优先级：限制深度外环对 pitch 的激进程度

在 heading 问题修正后，再做这一层更有意义。

优先尝试：

1. 适度降低 `control.depth.target_pitch_deg_max`，例如从 `15` 降到 `8~10` 做对比。
2. 适度降低 `control.pitch.kp`，避免深度外环一给目标俯仰，舵面就冲到极限。
3. 观察是否需要提高 `control.pitch.kd`，增强阻尼。

### 3.4 第四优先级：重新分配 yaw 与 depth 的舵面权重

如果后续确认确实需要同时做深度和航向高动态控制，建议在 [algorithm/auv_pid_controller.py](../algorithm/auv_pid_controller.py) 增加更明确的控制分配逻辑，例如：

1. 先分别计算 elevator/rudder 请求。
2. 在组合成四片舵之前做权重裁剪。
3. 当总命令接近限幅时，明确设定 depth 优先或 yaw 优先，而不是简单叠加后裁剪。

这是中期优化项，不是第一轮联调必须完成的动作。

### 3.5 第五优先级：为控制器增加调试可视化

建议在 [brain_linux/src/auv_controller/auv_controller/auv_controller_node.py](../brain_linux/src/auv_controller/auv_controller/auv_controller_node.py) 新增一类调试输出，至少包含：

- `depth_error`
- `yaw_error`
- `target_pitch`
- `pitch_saturated`
- `yaw_saturated`
- `thrust_saturated`

原因很直接：当前 `AUVPIDController.compute()` 已经返回了 debug 字段，但 node 层没有把这些信息发布出来，导致调参时只能看最终 `/cmd_vel`，定位效率偏低。

## 4. 当前建议的执行顺序

建议不要直接进入“大范围调 PID”，而是按下面顺序推进：

1. 先补 `target_heading_rad` 的来源。
2. 再确认角速度反馈是否有效。
3. 再观察饱和是否显著缓解。
4. 最后才细调 `pitch/yaw/depth` 参数。

## 5. 一句话结论

当前控制问题的第一根因不是 protocol_udp，也不是速度环，而是“决策层没有给有效航向目标，控制器却默认拿 0 度做目标”，再叠加“角速度反馈缺失”和“舵面分配较粗”，最终把 yaw/pitch 舵面长期推到限幅附近。

## 6. 2026-04-01 增量验证结果

在本文档形成后，已经进一步实现并验证了两项最小修复：

1. 决策层默认航向不再回退到固定 `0 rad`，而是以当前 yaw 为基准，再叠加横向误差修正。
2. 控制器在 `Odometry.twist.twist.angular.*` 近似为 0 时，会回退使用 `/auv/sensors/imu` 的角速度作为 `q/r` 反馈，并新增 `/auv/controller/debug` 调试话题。

### 6.1 修复后的关键观测

修复后抓到的实时样本如下：

- `/auv/control/setpoint`
  - `target_heading_rad = -0.86468`
- `/auv/controller/debug`
  - `rate_source = imu`
  - `yaw_error_deg = -0.032`
  - `current_yaw_deg = -33.011`
- `/cmd_vel`
  - `linear.x = 12.16`
  - `angular.x = 30.0`
  - `angular.y = 0.24`
  - `angular.z = -30.0`
  - `linear.z = -0.24`

### 6.2 这组结果说明什么

先前最严重的结构问题已经明显改善：

- yaw 误差已经从几十度量级降到接近 0。
- 控制器明确使用了 IMU 角速度，而不是继续吃全零角速度。
- rudder 对应的那组命令已经回到很小量级，不再是主导饱和源。

当前剩余主问题已经更聚焦：

- 深度误差仍然较大。
- elevator 对应的那组舵面仍在 `±30 deg` 附近打满。

换句话说，当前控制问题已经从“yaw 与姿态反馈都不可信”收敛为“depth/pitch 回路仍然过激或控制裕度不足”。

### 6.3 下一步优先级因此发生了变化

在这一轮修复后，建议把后续动作顺序调整为：

1. 继续保留当前航向修复，不要再回退到固定 `0 rad`。
2. 优先围绕 depth/pitch 做调试与调参。
3. 首先尝试降低 `control.depth.target_pitch_deg_max`。
4. 然后再看是否需要降低 `control.pitch.kp` 或提高 `control.pitch.kd`。

这意味着：yaw 环不再是当前第一矛盾，后续探索应转向 depth/pitch 饱和问题。
