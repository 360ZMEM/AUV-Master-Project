# Foxglove 整合落地计划（2026-03-24）

本文档用于指导将 `Console上位机软件/ros2_ws/foxglove_layout_project` 的 Foxglove 能力，逐步整合进 `AUV_Master_Project`。核心原则是：**优先模仿已有实现，不自行发明新的布局语义，不让 Foxglove 生成器与发布端产生额外歧义**。

## 1. 目标边界

本次整合的目标不是“重写一套 Foxglove 体系”，而是将已有能力平移到新仓库，确保以下三件事始终一致：

1. 话题名和字段路径一致
2. 布局 JSON 结构一致
3. 运行时数据流一致

换句话说：
- 先对齐 topic contract
- 再对齐 layout generator
- 最后才考虑新增 Zenoh 发布项

## 3. 为什么要尽量“模仿已有实现”

Foxglove 这类功能最怕两种歧义：

1. **布局歧义**：生成器与导入布局的结构不一致，导致面板显示异常。
2. **topic 歧义**：发布端认为 topic 是 A，布局端绑定的是 B，最后表面上“有图”，实际上看的是错数据。

因此，整合时必须遵守以下规则：

- topic 统一由一个配置文件管理
- 布局 builder 不直接写硬编码字符串
- 生成 JSON 的字段顺序和结构尽量稳定
- 新增 panel 类型必须先在参考项目里找对应写法，再迁移
- 不要依赖“看界面猜结构”，而要依赖 generator 和 SDK 的真实 API

## 4. 在 AUV_Master_Project 中的推荐放置方式

建议把 Foxglove 相关内容分成三层：

### 4.1 配置层
建议新增一个独立配置文件，例如：
- `AUV_Master_Project/<某个工具目录>/config/foxglove_topics.py`
- 或 `AUV_Master_Project/<某个工具目录>/config/foxglove_topics.yaml`

职责：
- 定义 topic 名称
- 定义字段路径
- 定义颜色和标题
- 定义可选命名空间前缀

### 4.2 生成层
建议新增一个生成器目录，例如：
- `AUV_Master_Project/<某个工具目录>/generator/`

职责：
- 读取 topic 配置
- 构造 `configById`
- 构造 `layout` 树
- 输出 `layout.json` 和 `meta.json`

### 4.3 运行层
如果后续要引入 live server 或 MCAP，可以单独加一个工具脚本，例如：
- `run_foxglove_server.py`
- `record_foxglove_mcap.py`

职责：
- 与生成器解耦
- 与 ROS2 启动链路解耦
- 不影响现有仿真和脑端主流程

## 5. 建议的第一版布局内容

第一版不要过度扩展，建议先与参考项目保持同级复杂度：

- 3D 面板：载具空间姿态和轨迹
- Plot 面板：深度、温度、压力
- RawMessages 面板：IMU、状态、Twist
- 可选 Map 面板：如果数据和 frame 条件允许再启用

### 推荐原则
- 先复用当前已验证过的面板类型
- 先复用当前已有的数据源
- 先不引入自定义 panel 或过多脚本节点

## 6. 布局生成的固定约束

为了避免歧义，生成器应该遵守以下固定约束：

### 6.1 单一 topic 真值源
所有 topic 名称统一放在一个配置对象里，类似参考实现中的 `TopicConfig`。

### 6.2 命名空间前缀可选
支持 `/sim` 之类前缀，但前缀拼接规则必须固定，不能在多个地方各写一套。

### 6.3 面板 key 固定格式
建议保持参考实现的风格：
- `Plot!depth`
- `3D!auv3d`
- `RawMessages!imu`

这样导出的 `configById` 和 `layout` 树更容易 diff 和排查。

### 6.4 输出文件稳定
布局 JSON 和 meta 文件应当：
- 允许重复生成
- 允许 git diff
- 允许直接导入 Foxglove Desktop

## 7. Foxglove SDK 在本项目中的正确使用方式

### 7.1 适合做的事
- 生成布局 JSON
- 通过 `start_server()` 做可选 live visualization
- 通过 `open_mcap()` 做可选录制
- 通过 `Channel` 和 `Schema` 发布结构化数据

### 7.2 不建议一开始就做的事
- 把 SDK 深度耦合进主控制逻辑
- 把 SDK 的布局类型直接散落到各个节点里
- 在未固定 topic contract 前就做复杂 live server 逻辑

### 7.3 示例模式必须对齐
请尽量模仿以下两种方式：
- `live-visualization/main.py`：说明如何起 server、怎么监听 client、怎么发消息
- `custom-protobuf/main.py`：说明如何建立 channel、schema、编码方式

这能避免自己推导一个“看起来像 Foxglove 但其实不兼容”的接口层。

---

## 8. 新增 Zenoh 发布项的约束

你提到后续可能还要新增 Zenoh 发布项，这里必须明确：

### 正确顺序
1. 先定义 Foxglove 需要展示什么
2. 再确认这些数据是否已经在发布链路上存在
3. 如果不存在，再新增 Zenoh topic
4. 最后把这个 topic 加入布局

### 不建议的顺序
- 先把所有 topic 都往 Zenoh 里加
- 再临时想 Foxglove 怎么看

因为这会造成：
- topic 命名漂移
- 字段路径不稳定
- 布局面板与实际数据脱节

## 10. 推荐实施节奏

### Phase 1：只做布局生成
- 搬 topic 配置
- 搬 layout builder
- 生成 JSON
- 导入 Foxglove Desktop 验证

### Phase 2：补 live server 或 MCAP
- 只在需要时加入 `start_server()` 或 `open_mcap()`
- 不改变主链路的 topic contract

### Phase 3：再扩 Zenoh 发布项
- 只增加 Foxglove 已经有对应面板消费的数据
- 每新增一个 topic，都做一次布局回归

## 11. 验证标准

以下条件都满足时，才算整合没歧义：

1. 布局 JSON 可重复生成，内容稳定
2. Foxglove Desktop 导入不报 panel type 或 topic 错误
3. 3D、Plot、RawMessages 的数据能按预期显示
4. 参考项目和新仓库的 topic 命名方式一致
5. 新增 Zenoh 发布项后，布局无需猜测即可绑定
6. 如启用 live server，`foxglove.start_server()` 能稳定连接
7. 如启用 MCAP，`foxglove.open_mcap()` 的记录可回放并保持布局一致

- topic 和字段路径只有一个真值源
- 新增 Zenoh 发布项必须服务于已经定义好的布局
