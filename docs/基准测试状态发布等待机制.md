# 基准测试状态发布等待机制

## 问题背景

在运行透明度分层基准测试时，分析工具报告缺少 `/auv/state/filtered` 样本，导致所有指标显示为 `nan`。这个问题的根本原因是节点启动顺序和数据流依赖。

## 技术分析

### `/auv/state/filtered` 发布条件

`/auv/state/filtered` 由 `auv_localization_node` 发布，该节点的输出依赖于以下条件：

1. **节点必须启动完成**：`auv_localization_node` 需要完全初始化，包括：
   - 加载 ES-EKF 滤波器配置
   - 创建发布器和订阅器
   - 启动定时器循环

2. **传感器数据必须可用**：ES-EKF 滤波器需要以下传感器输入才能产生有效状态估计：
   - `/auv/sensors/imu` (sensor_msgs/Imu)
   - `/auv/sensors/dvl` (geometry_msgs/TwistStamped)  
   - `/auv/sensors/depth` (std_msgs/Float32)

3. **滤波器必须初始化**：ES-EKF 需要至少一组完整的传感器数据来初始化状态向量。

### 数据流依赖链

```
仿真启动 (HoloOcean)
    ↓
传感器桥接 (Zenoh/UDP)
    ↓
/auv/sensors/* 话题发布
    ↓
auv_localization_node 接收传感器数据
    ↓
ES-EKF 滤波器初始化
    ↓
/auv/state/filtered 开始发布
    ↓
其他节点（决策、控制）可订阅状态估计
```

### 问题表现

在原来的基准测试脚本中，使用固定时间等待（`sleep "$((WARMUP_S + 10))"`），这种方法的缺陷：

1. **时间不精确**：不同机器性能下，节点启动时间差异很大
2. **无状态验证**：不知道 `/auv/state/filtered` 是否真的开始发布
3. **资源浪费**：等待过长时间或时间不足都会影响测试效率
4. **难以诊断**：当测试失败时，无法确定是节点未启动还是数据流问题

## 解决方案

### 等待验证机制

新的基准测试脚本实现了智能等待验证机制，在开始录制 rosbag 之前验证关键话题的可用性。

#### 实现细节

```bash
# 1. 初始等待，让系统有足够时间启动
sleep "$WARMUP_S"

# 2. 带超时的等待验证循环
wait_timeout=30
wait_start=$(date +%s)
while true; do
  # 检查超时
  if [[ $elapsed -ge $wait_timeout ]]; then
    echo "[AUV][WARN] timeout waiting for /auv/state/filtered"
    break
  fi

  # 检查话题是否存在
  if timeout 2 ros2 topic list | grep -q "/auv/state/filtered"; then
    # 验证是否有发布者
    pub_count=$(timeout 2 ros2 topic info /auv/state/filtered 2>/dev/null | grep -c "Publisher count:" || echo "0")
    if [[ "$pub_count" -gt 0 ]]; then
      # 等待第一条消息
      sleep 2
      break
    fi
  fi

  sleep 1
done
```

#### 机制优势

1. **状态驱动**：基于实际系统状态而非固定时间
2. **可配置超时**：30秒超时避免无限等待
3. **多层验证**：
   - 话题存在性检查
   - 发布者数量验证
   - 消息发布缓冲时间
4. **容错处理**：超时后继续执行，但记录警告

## 使用指南

### 基本使用

```bash
# 默认配置：6秒预热，20秒录制
./scripts/run_transparency_level_benchmark.sh

# 自定义预热和录制时间
./scripts/run_transparency_level_benchmark.sh --warmup 10 --duration 30
```

### 参数说明

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--warmup` | 6秒 | 初始等待时间，给系统启动的缓冲期 |
| `--duration` | 20秒 | rosbag 录制时长 |
| `--output-root` | `log/transparency_benchmarks` | 输出目录 |

### 关键话题

基准测试依赖以下话题的有效发布：

| 话题名称 | 消息类型 | 发布节点 | 用途 |
|----------|----------|----------|------|
| `/auv/state/filtered` | nav_msgs/Odometry | auv_localization_node | 状态估计，分析核心 |
| `/auv/diagnostics` | diagnostic_msgs/DiagnosticArray | auv_decision_node | 诊断信息，透明度指标 |
| `/auv/sensors/imu` | sensor_msgs/Imu | 桥接层 | 姿态和加速度数据 |
| `/auv/sensors/dvl` | geometry_msgs/TwistStamped | 桥接层 | 速度测量数据 |
| `/auv/sensors/depth` | std_msgs/Float32 | 桥接层 | 深度测量数据 |

## 故障排查指南

### 问题 1：等待超时

**现象**：
```
[AUV][WARN] timeout waiting for /auv/state/filtered after 30s
```

**可能原因**：
1. 仿真未正常启动
2. 传感器桥接失败
3. auv_localization_node 崩溃
4. 网络通信问题（Zenoh/UDP）

**排查步骤**：
```bash
# 检查节点是否运行
ros2 node list | grep auv

# 检查传感器话题是否发布
ros2 topic list | grep sensors

# 检查日志
tail -f log/transparency_benchmarks/<run_id>/level_*/launch.log
```

### 问题 2：有发布者但无消息

**现象**：
- `ros2 topic info` 显示有发布者
- 分析工具报告 "Missing estimated-state samples"

**可能原因**：
1. 传感器数据未到达 localization 节点
2. ES-EKF 初始化失败
3. 传感器数据格式错误

**排查步骤**：
```bash
# 检查传感器数据流
ros2 topic echo /auv/sensors/imu --once
ros2 topic echo /auv/sensors/dvl --once
ros2 topic echo /auv/sensors/depth --once

# 检查滤波器状态
ros2 topic echo /auv/state/filtered --once

# 查看节点日志
ros2 node info /auv_localization_node
```

### 问题 3：分析工具报告缺少诊断信息

**现象**：
```
Missing diagnostics samples. Check /auv/diagnostics
```

**可能原因**：
1. auv_decision_node 未启动
2. 决策节点未开始行为树执行
3. 诊断发布被禁用

**排查步骤**：
```bash
# 检查决策节点
ros2 topic list | grep diagnostics
ros2 topic echo /auv/diagnostics --once

# 检查行为树状态
ros2 topic echo /auv/bt_status --once
```

## 性能优化建议

### 预热时间调优

根据实际测试，不同系统的推荐预热时间：

| 系统配置 | 推荐预热时间 |
|----------|--------------|
| 高性能工作站 | 4-6 秒 |
| 笔记本电脑 | 8-12 秒 |
| 虚拟机 | 12-20 秒 |
| 远程SSH连接 | 增加 5 秒网络延迟 |

### 录制时长选择

根据测试目的选择合适的录制时长：

| 测试类型 | 推荐时长 | 说明 |
|----------|----------|------|
| 快速验证 | 10-15 秒 | 验证基本功能 |
| 性能基准 | 20-30 秒 | 收集足够样本 |
| 长期稳定性 | 60+ 秒 | 观察长期行为 |

## 代码实现参考

### 关键函数

等待验证机制的核心逻辑在 [run_transparency_level_benchmark.sh](../scripts/run_transparency_level_benchmark.sh) 中：

```bash
wait_for_filtered_state() {
  local wait_timeout=${1:-30}
  local wait_start=$(date +%s)
  
  while true; do
    local current_time=$(date +%s)
    local elapsed=$((current_time - wait_start))
    
    if [[ $elapsed -ge $wait_timeout ]]; then
      return 1  # 超时
    fi

    if check_topic_published "/auv/state/filtered"; then
      sleep 2  # 等待第一条消息
      return 0  # 成功
    fi

    sleep 1
  done
}
```
