# 基准测试状态发布等待机制 - 实施总结

## 变更概述

本次更新为透明度分层基准测试添加了智能等待验证机制，解决了 `/auv/state/filtered` 话题未被录制导致分析结果为 `nan` 的问题。

## 问题背景

### 原始问题

在运行 `./scripts/run_transparency_level_benchmark.sh` 时，分析工具报告：

```
Missing estimated-state samples. Check /auv/state/filtered
```

所有三个透明度级别（L1、L2、L3）的指标都显示为 `nan`。

### 根本原因

`/auv/state/filtered` 由 `auv_localization_node` 发布，该节点的输出依赖于完整的启动链：

1. HoloOcean 仿真启动
2. 传感器数据桥接（Zenoh/UDP）
3. `auv_localization_node` 初始化
4. ES-EKF 滤波器收到第一组传感器数据（IMU、DVL、深度）
5. 滤波器初始化完成
6. 开始发布 `/auv/state/filtered`

原始脚本使用固定时间等待（`sleep "$((WARMUP_S + 10))"`），无法验证话题是否真的开始发布。

## 解决方案

### 核心改进

在 [scripts/run_transparency_level_benchmark.sh](../scripts/run_transparency_level_benchmark.sh) 中添加了智能等待验证机制：

```bash
# 1. 初始等待，给系统启动缓冲
sleep "$WARMUP_S"

# 2. 带超时的验证循环（最多30秒）
wait_timeout=30
wait_start=$(date +%s)
while true; do
  # 检查超时
  if [[ $elapsed -ge $wait_timeout ]]; then
    echo "[AUV][WARN] timeout waiting for /auv/state/filtered after ${wait_timeout}s"
    echo "[AUV][WARN] proceeding with recording anyway"
    break
  fi

  # 检查话题是否存在
  if timeout 2 ros2 topic list | grep -q "/auv/state/filtered"; then
    # 验证是否有发布者
    pub_count=$(timeout 2 ros2 topic info /auv/state/filtered 2>/dev/null | \
                grep -c "Publisher count:" || echo "0")
    if [[ "$pub_count" -gt 0 ]]; then
      # 等待第一条消息
      sleep 2
      echo "[AUV] /auv/state/filtered is active, starting recording"
      break
    fi
  fi

  echo "[AUV] still waiting for /auv/state/filtered... (${elapsed}s/${wait_timeout}s)"
  sleep 1
done
```

### 机制特点

1. **多层验证**：
   - 话题存在性检查
   - 发布者数量验证
   - 消息发布缓冲时间

2. **超时保护**：30秒超时避免无限等待

3. **容错处理**：超时后继续执行，但记录警告

4. **状态驱动**：基于实际系统状态而非固定时间

## 技术细节

### 数据流依赖链

```
仿真启动 (HoloOcean)
    ↓
传感器桥接 (Zenoh/UDP)
    ↓
/auv/sensors/* 话题发布
    ↓
auv_localization_node 接收传感器数据
    ↓
ES-EKF 滤波器初始化
    ↓
/auv/state/filtered 开始发布 ← 等待机制验证这里
    ↓
开始录制 rosbag
```

### 关键话题

| 话题名称 | 消息类型 | 发布节点 | 用途 |
|----------|----------|----------|------|
| `/auv/state/filtered` | nav_msgs/Odometry | auv_localization_node | 状态估计 |
| `/auv/diagnostics` | diagnostic_msgs/DiagnosticArray | auv_decision_node | 诊断信息 |
| `/auv/sensors/imu` | sensor_msgs/Imu | 桥接层 | 姿态和加速度 |
| `/auv/sensors/dvl` | geometry_msgs/TwistStamped | 桥接层 | 速度测量 |
| `/auv/sensors/depth` | std_msgs/Float32 | 桥接层 | 深度测量 |

## 故障排查

### 等待超时

**现象**：
```
[AUV][WARN] timeout waiting for /auv/state/filtered after 30s
```

**解决方案**：
1. 增加预热时间：`--warmup 10`
2. 检查系统资源是否充足
3. 查看启动日志：`cat log/transparency_benchmarks/<run_id>/level_*/launch.log`
4. 使用验证脚本检查系统状态

### 仍然出现 nan

**现象**：等待成功但分析结果仍为 nan

**排查步骤**：
```bash
# 检查rosbag内容
ros2 bag info log/transparency_benchmarks/<run_id>/level_1/rosbag

# 检查分析日志
cat log/transparency_benchmarks/<run_id>/level_1/analyze.log

# 手动运行分析
python3 tools/analyze_bag.py log/transparency_benchmarks/<run_id>/level_1/rosbag
```

## 性能影响

### 时间成本

- **等待时间**：最多 30 秒（通常 6-12 秒完成）
- **总测试时间**：预热时间 + 等待时间 + 录制时长 × 3 个级别

### 资源使用

- **内存**：增加最小（仅额外存储时间戳）
- **CPU**：每秒执行一次 `ros2 topic list` 和 `ros2 topic info`
- **网络**：仅用于查询话题信息，不产生额外流量
